# 보고서 작성 스킬 · 구현 기준 스펙

기록일: 2026-09-09 · 최근 정리: 2026-09-10

## 0. 문서의 역할과 결정 상태

이 문서는 작성 스킬을 구현할 때 따를 단일 기준 스펙이다. **확정된 규칙과 검토안을 함께 포함**하며, 해당 절의 상태 표시와 §6을 따른다. 최신 사용자 지시가 문서와 다르면 기준 스펙을 갱신하고, 과거 예시·검토 기록보다 우선한다. 문서 정리는 미확정 정책이나 스킬 구현에 대한 승인을 뜻하지 않는다.

스킬 구현 계획은 §5의 인계 규칙을 따른다. 개발 상태와 Git 사용법은 [README](../../../README.md), 정리 전후 대응은 [작업 메모의 정리 기록](2026-09-09-integrated-distiller-writing-example-notes.md#spec-refactor-audit)에 둔다.

## 1. 용도·입력·산출물

자료 또는 기존 초안과 작성 조건을 받아 핵심을 선택하고 필요한 설명을 조직하여 원고를 작성·재작성한다. 논문을 포함한 보고서 전반에 적용하며, 첫 적용 대상은 결과보고서다. 기존 초안에서는 잘된 설명을 살리고 핵심을 가리는 내용과 배치를 다듬는다.

- **입력:** 실험 기록·메모·관련 자료·기존 초안, 목적·독자·문서 유형·필수 형식·표현 방식·강조점, 대화에서 보완한 미세한 의도와 설명 방향.
- **산출물:** 작성 조건과 짧은 작성안, 참조가 연결된 스펙시트, 실제 설명을 담은 라이팅 플랜, 원고와 그림에 사용할 텍스트. 단계별 상세는 §2에 정의한다.
- **실행 범위:** 사용자가 명시적으로 호출하는 작성 스킬 하나를 단일 에이전트가 수행한다. AGENTS.md 자동 실행은 넣지 않는다. 별도 피드백 스킬과 서브에이전트 방식은 후속 작업으로 보류한다.
- **피규어:** 생성하지 않는다. 플랜에서는 전달할 핵심을 정하고, 라이팅에서는 삽입 자리·실제 설명·캡션·각주와 연결된 제작 메모를 준비한다.

## 2. 개념·자료 인계·네 단계

### 2.1 검토 단위와 제목의 역할

| 단위 | 정의 |
|---|---|
| 섹션 | 스펙에서 제목·하나의 설명 목표·범위를 배정한 내용 단위. 여러 문단과 표시용 소제목을 포함할 수 있다. 스펙에서 목표·범위를 배정한 하위 섹션은 별도 섹션이며, 상위 섹션은 그 목표들을 묶는 역할과 흐름을 맡는다. |
| 표시용 소제목 | 기존 섹션의 설명을 읽기 쉽게 묶거나 예고하는 표현 구획. 소속 섹션의 목표·범위를 따르며, 별도 스펙 행이나 별도의 핵심을 요구하지 않는다. |
| 설명 문장 | 플랜에서 핵심의 이해·근거·해석에 기여하는 문장 또는 문장형 항목. 최종 원고의 문장 수·문단 경계를 고정하지 않는다. |
| 문단 | 라이팅에서 하나의 설명 흐름을 묶는 표현 단위. 모든 문단에 제목을 붙이거나 섹션 핵심을 반복하지 않는다. |

제목의 Markdown 수준·번호·글꼴이나 스펙에 적혀 있다는 사실만으로 역할을 판정하지 않는다. **실제 내용이 어느 섹션의 승인된 목표·범위에 속하는지** 확인하고 그 대응을 작업 기록에 남긴다. 기존 목표의 하위 설명을 묶으면 표시용 소제목이며, 독립 목표·범위를 새로 맡기거나 기존 핵심을 분리·변경하면 §3.5의 스펙 변경이다. 제목의 구획과 그 아래 내용의 변경 수준은 별도로 판단한다.

### 2.2 자료 풀과 참조 포인터

브레인스토밍 풀에는 원자료의 위치와 내용 안내, 대화에서 확인한 의도·선택 이유·강조점·조건·제외 범위를 보존한다. 원자료를 모두 복사하거나 요약으로 대체할 필요는 없으며, 필요한 원문과 근거로 돌아갈 수 있게 연결한다. 미채택 자료도 접근 가능하게 남기고, 대화나 확인으로 자료가 보완되면 기록을 갱신한다. 내부 후보와 승인 결정의 경계는 §3.2를 따른다.

스펙의 **우선 참조 = 자료 위치 + 참고할 내용 또는 이유 한 구절**이다. 필요하면 절·쪽·슬라이드·기록 항목을 붙여 관련 부분을 찾게 한다. 폴더 전체보다 해당 핵심에 유용한 자료를 가리키고, 사실 근거와 사용자 의도 포인터의 역할이 참조 이유에서 드러나게 한다.

플랜은 스펙의 목표·범위를 기준으로 연결된 원문을 먼저 읽고, 필요하면 더 넓은 풀에서 실제 설명과 근거를 선택한다. 포인터의 안내만으로 내용을 추측하지 않는다. 포인터는 사용할 자료의 한정 목록도, 전부 본문에 넣어야 할 목록도 아니다. 모든 자료를 매 섹션마다 다시 읽을 필요는 없다.

최초 플랜에서는 승인된 목표·범위 안에서 하위 설명·표시용 소제목·자료를 선택하고 포인터를 보완하는 것이 정상적인 확장이다. 자료나 포인터의 추가만으로 별도 승인을 요구하지 않는다. 목표·범위가 바뀌거나 이미 승인된 플랜의 필수 설명·근거 의미를 바꾸는 경우에는 §3.5를 적용한다.

### 단계 1. 글감 브레인스토밍

**입력:** 제공된 글감·기존 초안·작성 조건과 현재 사용자 지시.

**수행·산출물:** 자료를 파악하고 사용자와 대화하며 글감과 미세한 의도·강조점을 보완한다. 그룹 1·2로 목적·독자·형식·표현 방식과 전체 흐름을 정한다. 핵심 선택을 좌우하는 자료 누락이나 의도의 불확실성은 해당 문제를 질문하여 해결한다. 자료 풀과 함께 **작성 조건·큰 구성 방향을 담은 짧은 작성안**을 제시한다. 세부 제목과 설명 문장의 확정은 후속 단계에서 한다.

**완료 기준 · 검토안:** 목적·독자·형식·강조점·대략적인 범위와 큰 흐름이 정리되고, 제공된 글감과 사용 가능한 자료·위치가 파악되며, 스펙의 핵심 선택을 바꿀 미해결 질문이 없다. 모든 자료의 완독이나 세부 문장 확정은 요구하지 않는다. 작성 조건·구조·진행 승인은 §3.1을 따르며, 기존 초안의 후보를 함께 준비하는 예외는 §3.6을 따른다.

### 단계 2. 스펙시트

**입력:** 승인된 작성 조건·큰 흐름, 자료 풀. §3.6의 첫 묶음 검토에서는 작성 조건 후보에서 스펙 후보를 준비할 수 있다.

**수행·산출물:** 각 의미상 섹션에 **제목 하나·핵심 하나·짧은 우선 참조**를 대응시킨다. 핵심은 하나의 설명 목표 또는 전달 메시지다. “메모리 최적화 방안을 설명한다”처럼 목표형 문장을 허용하되 제목과 함께 대상·범위를 드러낸다. 여러 독립 목표를 한 문장에 이어 붙여 형식적으로 핵심 하나로 만들지 않는다.

그룹 3·4·5를 모든 섹션에 적용하여 제목과 핵심의 대응, 중심 목표의 단일성, 필요한 배경·이유·근거의 유무와 주장 범위를 확인한다. 상세 설명 후보·자료 대조·점검은 연결된 작업 기록에 보존하고, 사용자에게는 작성 조건에 연결된 짧은 전체 스펙시트를 제시한다.

**완료 기준 · 검토안:** 모든 섹션의 제목·핵심·범위가 대응하고, 핵심을 설명할 근거와 그 위치가 연결되어 있다. 필요한 목표의 누락·불필요한 중복이 해소되며, 전체 순서가 작성 목적과 이해의 선후관계에 맞는다. 상세 자료 접근을 유지하면서 검토물은 간결해야 한다.

### 단계 3. 라이팅 플랜

**입력:** 승인된 스펙, 작성 조건·강조점, 포인터로 연결된 자료·설명 기록, 보충 자료를 찾을 수 있는 브레인스토밍 풀. 기존 초안의 첫 검토용 스펙·플랜 후보는 §3.6의 조건에서 함께 준비할 수 있다.

**수행·산출물:** 각 섹션의 목표를 **실제로 전달할 설명**으로 확장하고 순서를 정한다. 필요한 개념·선택 이유·작동 과정·근거·해석 조건을 짧은 문장이나 문장형 항목으로 배치한다. 예를 들어 앞 단계의 목표는 “활성화한 증류 경로에 필요한 티처 모듈만 GPU에 올린다”처럼 실제 방안으로 구체화한다. 목표나 집필 지시를 반복하는 것만으로 플랜을 완성하지 않는다.

그룹 3·4·5를 섹션과 각 설명 문장에 적용해 제목의 범위, 중심 메시지 유지, 필수 설명의 충분함과 각 문장의 역할을 확인한다. 정의·예시·조건·앞뒤 연결도 이해나 판단에 필요하면 유지하며, 핵심을 직접 반복할 의무는 없다. 필요한 그림은 중심 메시지만 적는다. 최종 문장 표현·문단 구성은 라이팅에서 다듬는다.

**완료 기준 · 검토안:** 스펙의 모든 목표·범위가 플랜에 대응하고, 표시용 소제목과 설명의 소속이 분명하다. 실제 설명과 필수 연결이 갖춰지고 역할 없는 반복·설명 공백이 해소되며, 문장·섹션의 선후관계와 필요한 그림의 핵심이 정리되어 있다. 모든 섹션을 점검한 전체 플랜을 제시한다.

### 단계 4. 글 라이팅

**입력:** 승인된 플랜·작성 조건·연결된 자료. 기존 원고가 있으면 함께 사용한다.

**수행·산출물:** 그룹 6·7로 문단·문장·불렛·표와 강조를 구현한다. 그룹 1·2의 작성 조건과 전체 흐름, 그룹 3·4·5의 제목 범위·핵심·필수 설명·근거는 보존한다. 앞서 추린 핵심을 매번 새로 선정하지 않는다. 그림의 실제 설명·캡션·각주·삽입 자리와 의도·내용·간단한 스케치 구성의 제작 메모는 §4.2의 G7-4에 따라 준비한다.

**완료 기준 · 검토안:** 승인된 핵심·필수 설명·근거·해석 조건이 원고에 유지되고, 문단과 섹션을 이어 읽을 때 흐름이 유지된다. 작성 형식과 §4의 적용 기준을 충족하고, 그림 생성 없이 필요한 텍스트를 준비한다. 표현·내용 변경은 §3.5, 최종 검토와 완료 승인은 §3.1을 따른다.

### 그룹별 적용 요약

일곱 그룹은 네 단계에서 사용하는 기준이며 독립된 실행 단계가 아니다. 같은 그룹도 단계마다 적용 목적과 깊이가 다르다.

| 그룹 | 1. 브레인스토밍 | 2. 스펙시트 | 3. 라이팅 플랜 | 4. 글 라이팅 |
|---|---|---|---|---|
| 1. 목적·독자·형식 | 작성 조건을 정함 | 조건에 맞는지 확인 | 조건에 맞는지 확인 | 조건과 표현 방식을 구현 |
| 2. 전체 구성·흐름 | 큰 역할과 순서를 정함 | 섹션 전체의 순서·누락·중복 점검 | 설명의 선후관계와 섹션 연결 점검 | 실제 읽는 흐름 점검 |
| 3. 제목 | 다룰 범위 탐색 | 핵심을 정확히 예고하는 제목 선택 | 각 설명이 제목의 범위에 속하는지 점검 | 제목과 실제 원고의 일치 유지 |
| 4. 핵심 | 전달 의도 탐색 | 섹션마다 중심 설명 목표·메시지 하나를 선별 | 설명을 확장해도 같은 핵심을 유지 | 승인된 핵심이 드러나는지 확인 |
| 5. 설명·근거 | 필요한 글감 수집 | 핵심의 설명 가능성과 근거를 내부 확인 | 필요한 설명을 구성하고 문장별 역할 점검 | 필수 설명·근거·해석 조건 보존 |
| 6. 문단·문장·용어 | 용어 등 작성 조건 확인 | 핵심의 의미가 모호하지 않게 작성 | 설명 관계가 판단될 정도로 작성 | 문단·문장·용어를 집중적으로 다듬음 |
| 7. 표현 형식·위계 | 원하는 표현 방식 확인 | 짧고 검토 가능한 형태 유지 | 설명 순서와 그림의 핵심을 계획 | 줄글·불렛·표·그림 설명과 강조 수준 구현 |

## 3. 자체 점검·승인·변경·재개

### 3.1 공통 진행과 승인

단일 에이전트가 모든 섹션과 전체 문서를 먼저 점검·수정하고, 사용자는 정리된 **단계 전체 산출물**을 검토한다. 사용자가 분할 검토를 요청한 경우에만 지정 범위로 나눈다. 섹션별·문단별 사용자 승인이나 별도 그룹 6·7 승인 단계를 추가하지 않는다.

1. 해당 단계의 산출물을 작성하고 적용되는 체크 항목의 미충족 사항을 수정한다.
2. 전체 산출물의 내용·구조를 검토받고, 피드백 반영 후 영향을 받는 항목과 전체 흐름을 다시 확인한다.
3. 현재 버전·범위의 내용·구조 승인과 단계 전환 승인을 기록한다. 한 답변이 이들을 명시적으로 함께 승인하면 그대로 인정한다.
4. **자체 체크리스트 충족 + 단계 전체 내용 승인 + 구조 승인 + 진행 승인**이 모두 갖춰지면 다음 단계로 넘어간다. 최종 라이팅은 전환 대신 원고 완료 승인을 받는다.

자체 점검은 사용자 승인을 대신하지 않으며, 부분 승인이나 특정 부분에 대한 긍정적 의견을 전체 승인으로 확대하지 않는다. 미충족·미승인 범위는 수정하고, 사용자 의도·자료가 필요하면 해결할 질문을 구체적으로 제시한다. 기존 초안의 첫 진입은 §3.6에 따라 후보 준비와 검토 요청을 묶을 수 있으며, 단계별 점검·승인 범위는 유지한다.

이 절은 SKILL.md에 명시할 필수 진행 절차다. SKILL.md만으로 시스템 수준의 실행 차단이 보장되는 것은 아니다.

### 3.2 승인 범위와 인계 경계

승인은 검토한 산출물의 **버전·범위**에 적용된다. 이미 승인한 범위와 구체적인 사용자 지시의 승인 효력을 인정하고 같은 사항을 반복해서 묻지 않는다. 변경된 결정은 §3.5로 처리하며, 미변경 범위의 승인은 유지한다.

다음 두 경계의 세부 문구는 **검토안**이다.

- **내부 기록과 승인 결정:** 글감의 설명 후보·선택 이유·검토 중 순서는 참고 기록이다. 핵심의 의미나 성립 범위를 좌우하는 조건은 사용자에게 보여주는 핵심이나 연결된 짧은 조건으로 드러낸다. 미제시 후보를 승인 결정으로 취급하지 않는다.
- **변경 범위와 새 내용:** 범위 승인은 해당 수정안을 준비할 수 있다는 뜻이다. 제시한 구체적 수정 내용과 사용자가 직접 지시한 결정은 승인 범위로 인정하며, 아직 제시하지 않은 새로운 설명 결정은 다음 산출물 검토에 포함한다.

### 3.3 체크리스트 기록

각 항목에 **확인할 조건·적용 범위·상태·확인 위치와 짧은 근거**를 남긴다. 미충족 항목에는 필요한 수정을 기록한다. 통과는 검토를 수행했다는 뜻이 아니라 요구 상태가 충족되었다는 뜻이며, 발견한 결함을 기록만 남겨서는 통과하지 못한다.

- 필수 항목을 삭제하거나 해당 없음으로 처리하지 않는다. 그림 등 조건부 항목은 실제 적용 조건이 없을 때만 이유를 기록한다.
- 근거가 부족하거나 확인하지 않은 항목은 충족으로 표시하지 않는다.
- 내용·구조가 바뀌면 영향을 받는 항목을 다시 확인한다.
- 점검·승인·자료 대조 기록은 작업 기록에 두고 원고에는 독자에게 필요한 내용과 출처를 제시한다.

### 3.4 점검 범위

섹션별 점검의 기준 목록은 스펙의 섹션 목록이다. 목표·범위를 배정한 하위 섹션은 각각 점검하고, 상위 섹션은 하위 목표들의 역할과 흐름을 점검한다. 표시용 소제목은 별도 점검 단위를 늘리지 않으며 **표현은 그룹 3·6·7, 그 아래 설명은 그룹 4·5·6·7로 소속 섹션 안에서 모두 확인**한다. 어느 섹션에도 대응하지 않는 소제목·내용은 통과할 수 없다.

스펙에서는 섹션, 플랜에서는 섹션과 각 설명 문장, 원고에서는 문단·문장과 섹션 사이 연결을 확인한다. 단계별 완료 기준은 §2, 그룹 6·7의 원고 적용은 §4를 따른다. 모든 단계의 마지막에는 문서 전체의 누락·중복·순서와 흐름을 확인한다.

### 3.5 변경 처리

변경은 문장 수·분량·제목 추가 여부가 아니라 **승인된 결정의 의미가 달라지는지**로 구분한다. 앞 단계에 영향이 있어도 전체 브레인스토밍을 처음부터 반복하지 않는다.

| 구분 | 판단 기준 | 예시 | 처리 |
|---|---|---|---|
| 표현 보완 | 섹션의 핵심·범위, 필수 설명과 근거의 의미, 설명의 논리적 의존관계를 유지한다. | 문단 분리·병합, 줄글의 불렛 전환, 같은 내용을 묶는 소제목 추가, 의미를 보존한 제목 수정, 핵심 문장의 선제시, 필요한 연결 문장·용어 풀이·출처 표기 보완. | 에이전트가 수정하고 관련 체크 항목을 확인한다. 별도 재승인 없이 집필을 계속하며 단계 전체 원고 검토에 포함한다. |
| 라이팅 플랜 변경 | 섹션의 핵심은 유지하지만 필수 설명의 추가·삭제, 근거가 뒷받침하는 내용, 설명의 논리적 의존관계가 달라진다. | 핵심 이해에 필요한 작동 원리를 새로 추가, 필수 실패 분석을 본문에서 제외, 결론을 설명하는 비교 근거를 다른 지표로 교체. | 해당 플랜과 그에 의존하는 원고의 변경안을 준비해 묶음으로 승인받는다. 기존 스펙의 핵심이 유지되는지 확인한다. |
| 스펙 변경 | 섹션의 핵심·설명 범위·역할이나 문서의 주요 논리 구성이 달라진다. | 중심 기여를 바꿈, 독립된 주장을 가진 섹션을 추가·제거, 기존 핵심을 둘로 분리, 주요 섹션 순서를 바꿔 문서의 설명 경로를 변경. | 스펙 수정안과 관련 플랜의 변경 범위를 함께 제시한다. 변경 승인을 받은 뒤 영향을 받는 설명과 원고를 갱신한다. |

문서 목적·독자·필수 형식 자체를 바꿔야 한다면 그룹 1·2의 작성 조건도 함께 변경 대상으로 제시한다. 변경되지 않은 조건과 승인된 내용은 유지한다.

제목의 표시 구획과 내용 변경은 별개다. 기존 설명의 소제목 묶기·재배열은 의미와 논리적 의존관계를 유지하면 표현 보완이다. 새로운 필수 단계·전제·근거가 생기면 플랜 변경으로 처리한다. 승인된 개념의 짧은 풀이·예시나 출처 서식 보완은 표현 보완이지만, 새 주장·비교 근거·필수 원리를 보충하면 그 의미에 따라 플랜 또는 스펙 변경이다. 필수 근거 삭제나 해석 조건 은폐를 분량 축소로 처리하지 않는다.

실질 변경은 다음 순서로 처리한다.

1. **기존 내용·구체적 수정안·이유·영향 위치**를 한 묶음으로 준비한다. 스펙·플랜·원고뿐 아니라 요약·결론·그림 설명·각주·상호 참조의 영향도 확인한다.
2. 전체 맥락과 수정 부분을 제시해 변경 묶음의 내용·구조·진행을 검토받는다. 승인된 미변경 범위를 다시 승인받지 않는다.
3. 대기 중에는 영향을 받지 않는 집필·점검을 계속한다. 의존하는 부분도 검토용 수정안으로 준비할 수 있지만 승인된 원고로 확정하거나 다음 단계로 넘기지 않는다.
4. 승인 후 스펙·플랜·원고의 대응과 버전·승인 범위를 갱신하고, 영향받는 체크 항목과 전체 흐름을 다시 확인한다.

묶음 승인을 이후 다른 실질 변경의 포괄 승인으로 확대하지 않는다. 자료 확인 결과 주장을 유지할 수 없거나 중요한 근거가 부족하면 해당 부분을 통과시키지 않고, 근거에 맞는 수정안을 제시하며 의존 범위의 확정을 보류한다.

### 3.6 기존 초안의 진입과 재개

**결정 상태:** 기존 초안의 첫 묶음 검토 조건은 확정. 나머지 진입·재개 세부 기준과 최소 기록은 검토안이다.

진입점은 가장 뒤 단계의 파일 존재 여부가 아니라 확인된 작성 조건·승인 범위·남은 작업으로 정한다. 이미 제공된 조건·자료와 좋은 문단은 재사용한다.

| 입력 상황 | 먼저 확인할 내용 | 진입·검토 |
|---|---|---|
| 원자료만 있음 | 현재 지시와 자료에서 목적·독자·형식·강조점·범위를 파악하고, 방향을 좌우하는 누락만 질문한다. | 단계 1에서 작성 조건과 큰 흐름을 검토받고 스펙으로 진행한다. |
| 기존 초안만 있고 승인된 스펙·플랜이 없음 | 작성 조건·핵심·필수 설명·순서를 후보로 추출하고, 확인된 의도와 추정한 의도를 구별한다. 유지할 문단과 바꿀 결정을 연결한다. | 아래 확정 조건에 맞으면 후보를 묶어서 검토받는다. 초안과 추출 후보 자체를 승인 결정으로 보지 않는다. |
| 승인된 스펙이 있음 | 버전·승인 범위·작성 조건·자료 포인터와 플랜 진행 승인. | 단계 3 진입. 진행 승인만 빠졌다면 그 부분만 확인한다. |
| 승인된 플랜과 부분 원고가 있음 | 버전·승인 범위·집필 진행 승인과 기존 문단의 플랜 대응·작성·점검 상태. | 단계 4 재개. 맞는 문단을 유지하고 남은 부분을 작성하며, 다른 내용은 §3.5로 판정한다. |

현재 사용자가 특정 파일을 “승인된 플랜이니 이어서 써라”라고 지정해도 유효한 승인·진행 근거다. 옛 대화 재제출을 요구하지 않는다. 파일명이나 근거 없는 ‘승인됨’ 메모만으로 승인 사실을 추정하지 않는다.

#### 기존 초안의 첫 묶음 검토 · 확정

기존 초안과 현재 지시에서 목적·독자·형식·강조점·대략적인 범위·큰 흐름을 정리할 수 있고, 핵심 선택을 바꿀 미해결 질문이 없을 때 **작성 조건·스펙·플랜 후보**를 함께 준비한다. 초안에서 추정한 의도는 후보임을 표시한다. 방향을 바꿀 불확실성이 있으면 핵심 의도를 먼저 확인하며, 계속 미정이거나 사용자가 단계별 검토를 원하면 순서대로 검토받는다.

각 단계의 내용·구조를 자체 점검한 뒤, 작성 조건 → 섹션별 핵심 → 실제 설명·순서의 대응과 무엇을 유지·변경할지 한 묶음으로 보여준다. 사용자가 묶음의 내용·구조와 집필 진행을 승인하고 각 단계의 체크 조건이 충족되면 단계 4에 진입한다. 한 답변으로 함께 승인받을 수 있으며, 단계별 같은 승인을 반복하지 않는다.

일부만 승인되면 그 버전·범위의 승인을 보존하고 미승인 부분과 영향 범위만 다시 검토한다. 예를 들어 조건·핵심이 유지되고 플랜 순서만 수정되면 그 플랜을 다시 검토한다. 조건·핵심도 달라지면 그 영향까지 포함한다. 미승인 범위를 전체 승인으로 처리하거나 집필 단계로 넘기지 않는다.

이 예외는 기존 초안의 첫 진입에 적용한다. 원자료만 있는 신규 집필의 단계를 단축하거나 미제시 설명·미해결 조건을 승인하는 규칙이 아니다.

#### 최소 재개 기록 · 검토안

| 기록 | 남길 내용 |
|---|---|
| 작업·조건 | 대상 문서·수정 범위·목적·독자·형식·강조점·최신 지시 위치 |
| 참조 | 자료 풀·스펙·플랜·원고의 위치와 구별 가능한 버전 |
| 승인 | 버전·범위별 내용·구조·진행 또는 완료 승인과 사용자 발언·기록의 위치 |
| 진행 | 플랜 항목별 작성·점검 상태, 남은 작업·다음 위치. 작성됨·점검됨·승인됨 구별 |
| 미해결 | 필요한 자료·질문·변경안·영향 범위·승인 대기와 그동안 가능한 작업 |

재개할 때 승인 후 바뀐 결정만 확인한다. 빠진 포인터·기록은 필요한 범위를 복원하며 그 이유로 승인 구조 전체를 다시 설계하지 않는다. 근거가 부족한 주장과 의존 범위는 확정을 보류하고 독립 작업은 계속하되, 단계 전체의 통과 조건·승인 상태도 충족해야 한다. 기록 파일의 이름·저장 구성은 §6의 후속 결정이다.

## 4. 그룹 6·7의 작성 기준

### 4.1 역할·적용 범위 · 구체화안 검토

사용자는 그룹 6·7의 방향에 동의하고 구체화를 요청했다. 아래 세부 지침·통과 조건·적용 방식은 한 묶음의 검토안이다.

그룹 6은 문단·문장·용어로 설명을 연결하고, 그룹 7은 관계와 중요도를 형식으로 드러낸다. 작성 지침은 수행 행동, 통과 조건은 결과가 갖춰야 할 상태이며 작성 스킬의 자체 점검에도 같은 기준을 쓴다.

라이팅에서 집중 적용한다. 스펙·플랜에도 의미와 관계의 명확함을 요구하지만 최종 원고의 문단·서식을 요구하지 않는다. 승인된 핵심·필수 설명의 의미 변경은 §3.5를 따른다.

### 4.2 작성 지침과 통과 조건 · 구체화안

| ID | 작성 지침 | 통과 조건 |
|---|---|---|
| G6-1 | 문단이 맡은 설명 흐름의 요점을 앞부분에 두고, 필요한 이유·과정·근거·조건을 이어 쓴다. | 문단 앞부분에서 설명 대상과 요점을 식별할 수 있고, 뒤의 문장들이 같은 설명 흐름에 기여한다. 이해에 필요한 짧은 전제나 앞 문단과의 연결이 요점보다 먼저 올 수 있다. 요점이 이미 분명한 문단은 요약 문장을 추가하지 않고 유지한다. 문단마다 섹션의 핵심을 반복하거나 여러 작동 단계를 각각 독립 문단으로 쪼갤 필요는 없다. |
| G6-2 | 이유·방법·결과·해석의 관계와 설명에 필요한 선후관계를 문장과 문단 사이에 드러낸다. | ‘이것’, ‘해당 방식’, ‘이 결과’가 가리키는 대상을 식별할 수 있고, 독자가 필요한 정의나 중간 과정을 추측하지 않고 다음 설명을 이해할 수 있다. 내용만으로 관계가 분명하면 접속어를 덧붙이지 않아도 된다. ‘따라서’, ‘그 결과’를 추가하여 자료에 없는 인과관계를 만들지 않는다. |
| G6-3 | 원자료에 맞는 정확한 명칭을 일관되게 쓰고, 지정된 독자에게 필요한 용어만 처음 쓰거나 인접한 위치에서 짧게 설명한다. | 명칭만 보고 무엇을 다루는지 구별할 수 있으며, 정확한 ‘출력 토큰 임베딩’을 막연한 ‘정보’로 바꾸지 않는다. 정의는 현재 설명을 이해하는 데 필요한 범위를 갖춘다. 정확성을 이유로 무관한 구현 세부나 이미 충분한 용어 풀이를 추가하지 않는다. 약자는 뜻과 용법을 안내한다. U·M·P 같은 작업용 참조 표기는 자료·플랜에서 유지할 수 있으며 원고의 독자용 출처 표기와 구별한다. |
| G6-4 | 승인된 플랜의 필수 설명을 유지하면서 역할 없는 반복·당연한 부연·작성 과정의 기록을 줄인다. | 압축한 원고에서도 작동 조건·비교 기준·근거·해석 범위와 관측·해석·계획의 구분이 유지된다. 정의·예시·리캡은 없애면 이해나 판단이 끊기는 경우 유지한다. 원고에서 빠진 내용 때문에 다른 작동 방식이나 더 강한 결론으로 읽힌다면 미충족이다. 필수 설명을 삭제하거나 부록으로 옮겨 본문에서 판단할 수 없게 만드는 변경은 §3.5로 처리한다. |
| G7-1 | 정보가 이어지는 설명인지, 병렬 항목인지, 같은 기준의 비교인지 판단한 뒤 작성 형식 안에서 문단·불렛·표를 선택한다. | 문단은 이유·과정의 연결을 읽을 수 있고, 불렛은 병렬 관계와 각 항목의 의미를 알 수 있으며, 비교표는 공통 비교 기준을 확인할 수 있다. 형식 전환 후에도 필요한 설명과 인과관계가 남는다. 관계가 이미 분명한 짧은 문단은 유지한다. 병렬 내용이 있다는 이유만으로 불렛·표 전환을 강제하지 않는다. |
| G7-2 | 주 설명과 보충 설명의 역할에 맞춰 소제목·항목의 소속과 깊이를 정한다. | 표시용 소제목은 소속 스펙 섹션에 대응하고, 나란히 둔 같은 수준의 구획은 같은 상위 내용에 직접 속한다. ‘메모리 관리’와 ‘전체 역할 요약’처럼 맡는 역할이 달라도 같은 수준에 둘 수 있다. 섹션 전체 요약을 특정 하위 주제 아래에 잘못 묶지 않는다. 필수 조건은 해당 주장과 함께 읽고 찾을 수 있으며, 부연처럼 배치되어 주장의 성립 범위가 가려지지 않는다. |
| G7-3 | 핵심 메시지와 비교 목적에 맞춰 문장 배치·제목·굵기·여백 등으로 강조의 우선순위를 정한다. | 독자가 핵심과 보충 내용을 구별할 수 있고, 모든 문장이 같은 강도로 강조되지 않는다. 수치의 강조는 비교 대상·지표의 방향·실제 값에 맞으며, 해석을 바꾸는 조건도 함께 읽힌다. 특정 색상이나 소제목·불렛 개수, 반드시 하나만 강조하는 규칙은 요구하지 않는다. |
| G7-4 | 표·그림마다 전달할 메시지와 해석에 필요한 대상·조건·출처를 연결하고, 피규어의 텍스트와 삽입 자리를 준비한다. | 제목·인접 본문·캡션·각주를 함께 읽으면 설명 또는 비교 대상과 필요한 단위·조건·출처를 확인할 수 있다. 그림은 생성하지 않는다. 플랜에는 중심 메시지를 두고, 라이팅에서는 실제 설명·캡션·각주와 삽입 자리를 준비한다. 의도·내용·간단한 스케치 구성은 연결된 제작 메모로 남긴다. 아직 제작하지 않은 그림이나 확보되지 않은 검증 결과가 있는 것처럼 쓰지 않는다. |

문장 수·문단 길이·불렛 개수의 고정 수치를 통과 기준으로 삼지 않는다. 실패·개선 과정을 설명하는 절에서는 해결 방향과 그 의미를 먼저 제시하고 과정을 연결하되, 계획한 해결책과 실제로 확인한 결과를 구별한다. 모든 문단을 같은 ‘목표·문제·성과’ 틀로 반복하지 않는다.

필수 설명은 문구나 문장 수가 아니라 의미로 보존한다. 문장을 합치거나 짧게 써도 작동 조건·비교 기준·근거·해석 범위를 동일하게 확인할 수 있으면 표현 보완이다. 그 정보 자체가 삭제되거나 의미가 달라지는 경우에 §3.5의 변경 규칙을 적용한다.

### 4.3 짧은 지시에 따른 표현 방식 · 구체화안

| 사용자 지시 | 작성·점검 방식 |
|---|---|
| 가독성을 중시하라 | 결과보고서형을 기본으로 핵심을 먼저 보이고, 관계에 맞는 소제목·불렛·여백·표와 연결된 문단을 활용한다. 훑어보면 핵심과 하위 설명의 관계가 보이고 이어 읽으면 설명이 끊기지 않아야 한다. |
| 논문형으로 작성하라 | 지정 양식 안에서 문단 중심으로 요점·이유·근거·해석을 연결하고 다음 문단으로 이어지게 한다. 비교에 필요한 표·그림은 양식에 맞게 사용하며, 줄글에서도 문단의 요점과 논리적 진행을 알 수 있어야 한다. |

표현 방식은 작성 조건에 저장해 유지한다. 이미 논문형·필수 양식이 정해져 있으면 가독성 요청은 그 안에서 적용하고, 별도 형식 변경 지시 없이 결과보고서형으로 바꾸지 않는다. 두 형식 모두 핵심·근거·필수 조건을 보존하며 설명량·정확성의 차이로 해석하지 않는다. 짧은 지시 하나로 작성·자체 점검에 적용하며 사용자가 기준을 매번 나열할 필요는 없다.

[형식별 비교 예시](2026-09-09-integrated-distiller-writing-example.md#format-comparison)는 같은 내용을 다르게 배치하는 방법을 보여준다. 실제 스킬이 항상 두 버전을 출력할 의무는 없다.

### 4.4 원고의 자체 점검 · 구체화안

작성 조건·승인된 스펙·플랜에 대조하여 모든 섹션의 원고와 표시용 소제목 아래 내용을 G6-1~G7-4로 확인한다. 결과보고서형은 핵심·하위 설명의 배치를 훑은 뒤 이어 읽고, 논문형은 문단의 요점과 문단 간 연결을 중심으로 이어 읽는다. 전체 흐름·핵심 보존을 확인하고, 미충족 사항과 실질 변경은 §3에 따라 처리한다.

점검 기록은 §3.3의 섹션·기준 ID·상태·위치·근거로 남긴다. 표·그림이 없으면 해당 조건부 부분만 이유를 적어 해당 없음으로 처리하며, 설명 관계·용어·핵심 보존 기준은 계속 적용한다. [미충족 표현과 수정 사례](2026-09-09-integrated-distiller-writing-example-notes.md#writing-cases)에서 통과·미충족의 경계를 확인한다.

## 5. 구현 계획으로의 인계와 참조

Superpowers의 `writing-plans`는 **이 스킬을 제작하는 구현 계획**을 만든다. §2 단계 3의 **보고서 라이팅 플랜**과 목적·형식이 다르다.

최종 설계 검토 후 `docs/superpowers/plans/`에 하나의 구현 계획을 작성한다. 계획의 `Spec`은 이 파일을 가리키며, 각 작업에 **관련 요구사항·만들거나 수정할 파일·지침과 양식의 실제 내용·검증 방법**을 대응시킨다. 참조 문서마다 별도 계획을 만들지 않는다. §6의 상태를 확인하고 미정 정책을 임의로 확정하지 않는다. 아래 문서 수는 스킬 실행 시 출력할 파일 수를 정하지 않는다.

| 자료 | 언제 무엇을 읽는가 | 권위 |
|---|---|---|
| 이 기준 스펙 | 구현 계획 작성 시 전체 규칙·예외·완료 조건과 결정 상태를 확인하고 각 요구사항을 작업에 대응한다. | 현재 요구사항의 기준. 검토안·미정 상태도 함께 따른다. |
| [연결 예시](2026-09-09-integrated-distiller-writing-example.md) | 단계별 산출물·자료 인계를 설계할 때 §1~§4를 읽어 상세도와 대응을 확인한다. 원고 표현을 설계할 때 형식별 비교도 읽는다. | 구체적 결과의 예시. 실험 내용·문단 수·소제목 수·표 배치를 공통 규칙으로 확대하지 않는다. |
| [작업 메모](2026-09-09-integrated-distiller-writing-example-notes.md) | 자료 선택·근거 해석을 확인할 때 §1~§2, 점검·변경 처리를 설계할 때 §3의 판정 사례, 사용자 피드백의 의도를 확인할 때 §5~§6을 읽는다. | 이유·사례·검토 기록. 후보·자체 판단·사용자 동의를 구별한다. |
| [과거 비판적 검토](2026-09-09-report-writing-skill-critical-review.md) | 현재 규칙의 보완 이유가 필요할 때 해당 R 항목을 읽고 최신 스펙과 대조한다. | 당시 버전의 역사 기록. 현재 미해결 목록이나 추가 구현 스펙으로 사용하지 않는다. |

## 6. 결정 상태와 남은 검토

| 범위 | 현재 상태 |
|---|---|
| 스킬 용도·네 단계·자료 인계·검토 단위, 공통 점검·승인·세 수준 변경 | 확정된 방향과 진행 원칙. 단계별 완료 기준의 세부 문구는 별도 검토안이다. |
| 기존 초안의 첫 묶음 검토 | §3.6의 조건으로 확정. |
| 단계별 완료 기준·브레인스토밍 종료, 인계 경계, 기타 진입·재개와 최소 기록 | §2·§3.2·§3.6의 세부 검토안. |
| 그룹 6·7 | 방향 동의 후 §4의 구체화안 검토 단계. |
| 연결 예시 | 원고 방향에 대한 긍정적 평가와 U·M·P·S 표기 유지에 동의. 스킬 전체의 최종 승인과 구별한다. |
| 구현 계획·실제 SKILL.md | 작성·구현·설치 전. |

남은 작업은 다음과 같다.

1. 그룹 6·7 구체화안과 기타 인계·완료·재개 기준의 남은 문구를 검토한다. 이미 확정된 결정은 재승인하지 않는다.
2. 예시 보완 후보로 ITC의 짧은 실패·개선 선별 사례, 목차·섹션별 핵심 배열을 통한 전체 흐름, 다른 주제에 대한 적용을 확인한다. 필요한 보완만 수행하며 사례 수를 고정된 통과 기준으로 삼지 않는다. [작업 메모 §5](2026-09-09-integrated-distiller-writing-example-notes.md)의 제안·한계와 사용자 피드백을 따른다.
3. 호출 이름과 실행 산출물·자료 풀·작업 기록의 파일 이름·저장 구성을 정한다. 개발 저장소의 현재 폴더 구성과 구별한다.
4. 최종 설계를 검토한 뒤 §5에 따라 구현 계획을 작성한다.
