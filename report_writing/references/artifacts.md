# 산출물 계약

이 문서는 보고서 작업 파일과 상태의 단일 계약이다. Markdown 배치는 읽기 쉽게 조정할 수 있으나 필드의 의미와 연결을 유지한다. 별도 JSON 상태 엔진을 만들지 않는다.

<a id="identity"></a>
## 식별과 버전

문서 루트는 사용자 지정 경로, 재개 중인 기존 루트, `reports/<report-id>/` 순으로 선택한다. 새 기본 ID는 주제를 나타내는 짧은 이름으로 정하고 같은 이름의 기존 작업을 확인한다. 무관한 작업이면 구별 가능한 접미사를 붙인다.

각 산출물 머리에 문서명, 현재 버전, 사용한 선행 산출물과 버전을 적는다. 새 문서의 초기 버전은 `v0.1`이며 내용이나 구조가 바뀌면 식별 가능한 다음 버전을 사용한다. 기존 버전 방식이 있으면 유지한다. 기본 파일은 다음과 같다.

| 파일 | 역할 |
|---|---|
| `work/brief.md` | 작성 조건과 큰 흐름 |
| `work/materials.md` | 원자료와 사용자 의도의 참조 풀 |
| `work/spec.md` | 섹션별 제목·핵심·우선 참조 |
| `work/writing-plan.md` | 핵심을 실제 설명과 순서로 확장한 플랜 |
| `work/state.md` | 버전·승인·체크·진행·변경·다음 작업 |
| `report.html` | 독자가 읽을 최종 HTML 보고서 |
| `work/figures.md` | 필요한 그림의 제작 메모와 본문 연결 |

범례는 처음 한 번 둔다: `S` = Section, `P` = Plan, `M` = Material, `U` = User. P는 원고 한 문단과 같지 않다. 자료 ID와 플랜 ID는 수정 중에도 대응을 추적할 수 있게 유지한다. 독자용 원고에는 작업용 ID 대신 제목과 출처를 쓴다.

의미상 섹션은 제목·하나의 설명 목표·범위를 맡으며 여러 문단과 표시용 소제목을 포함할 수 있다. 새 목표·범위를 맡는 하위 섹션은 별도 S다. 표시용 소제목은 기존 S의 설명을 묶고 그 범위를 따른다. 제목 수준이나 번호만으로 구별하지 말고 실제 내용의 소속을 기록한다.

<a id="materials"></a>
## 자료 풀 · `work/materials.md`

각 항목에는 ID, 원자료/사용자 의도 구분, 원문 위치와 절·쪽·슬라이드·항목 등 locator, 내용 안내 또는 참조 이유, 확인 상태를 둔다. 원자료는 복사하거나 짧은 요약으로 대체하기보다 필요한 원문으로 돌아갈 수 있게 연결한다.

선택 이유, 미채택 자료와 이유, 조건, 제외 범위, 추정한 의도도 참고 기록으로 보존한다. 확인된 의도와 추정을 구별하고, 대화나 새 자료로 보완되면 갱신한다. 스펙의 우선 참조는 `위치 + 참고할 내용/이유`를 함께 가져야 한다. 포인터만으로 사실을 추측하거나 닫힌 목록·필수 수록 목록으로 취급하지 않는다.

<a id="brief"></a>
## 작성 조건과 짧은 작성안 · `work/brief.md`

다음을 포함한다.

- 목적, 독자, 문서 유형, 필수 형식, 표현 방식, 강조점, 범위, 제외 범위, 최신 사용자 지시 위치
- 큰 구성과 앞뒤 연결을 담은 짧은 작성안
- 핵심 선택에 영향을 줄 미해결 질문

`가독성을 중시하라`는 요청은 결과보고서형을 기본으로 핵심을 먼저 보이고 관계에 맞는 소제목·불렛·여백·표와 연결된 문단을 활용한다는 조건으로 저장한다. 이미 논문형이나 필수 양식이 있으면 그 안에서 적용한다. `논문형으로 작성하라`는 요청은 지정 양식 안에서 문단 중심으로 요점·이유·근거·해석과 다음 문단을 연결하는 조건으로 저장한다. 두 형식 모두 핵심·근거·필수 조건을 보존하며 항상 두 버전을 만들 필요는 없다.

brainstorm 체크는 다음과 같다.

| ID | 확인 조건과 적용 단위 |
|---|---|
| B1 | 전체 brief에서 목적·독자·형식·강조점·범위를 확인한다. |
| B2 | 전체 brief와 materials에서 큰 흐름과 자료 위치를 파악한다. |
| B3 | 핵심 선택을 바꿀 미해결 질문을 해소한다. |
| ALL-G12 | 전체 산출물에서 작성 조건 일치, 누락·중복·순서·흐름을 확인한다. |

<a id="spec"></a>
## 스펙 · `work/spec.md`

머리에 승인/후보 상태와 선행 brief 버전을 적는다. 각 의미상 S에는 제목, 하나의 핵심, 짧은 우선 참조를 둔다. 핵심의 성립 조건은 핵심 옆에서 보이게 하고 소속·범위가 모호하면 짧게 명시한다. 상세 설명과 점검은 work 기록에 연결한다.

| ID | 확인 조건과 적용 단위 |
|---|---|
| S-G3 | 모든 S에서 제목과 범위의 대응을 확인한다. |
| S-G4 | 모든 S에서 중심 목표 하나를 확인한다. 독립 목표를 한 문장에 이어 붙이지 않는다. |
| S-G5 | 모든 S에서 설명 가능성과 근거·조건 연결을 확인한다. |
| ALL-G12 | 모든 S와 상위 흐름에서 조건, 누락·중복·순서를 확인한다. |

예시:

> S8 · 증류 경로를 선택·조합하는 통합 증류기
>
> 핵심: 필요한 증류 방식을 선택해 함께 사용할 통합 증류기의 구현 방식을 설명한다.
>
> 우선 참조: U1 — 선택 기능을 중심에 둘 의도. M2 — 모듈 선별과 적재 순서. M3 — 같은 step의 이미지 인코딩 공유.

<a id="writing-plan"></a>
## 라이팅 플랜 · `work/writing-plan.md`

머리에 선행 spec·brief 버전을 적는다. S별 목표·범위 아래 P를 실제 설명 순서로 배치한다. 각 P에는 소속·역할, 실제 설명, 근거 M/U, 필요한 조건, 배치 지시를 둔다. 그림이 필요하면 중심 메시지도 둔다. 배치 지시는 실제 설명과 구별한다.

연결된 원문을 먼저 읽고 필요하면 더 넓은 materials로 확장한다. 최초 플랜에서 승인된 목표 안의 하위 설명·소제목·자료를 선택하는 것은 정상 확장이다. 승인된 플랜 뒤 필수 설명의 의미를 바꾸면 [변경 계약](workflow.md#changes)을 적용한다.

| ID | 확인 조건과 적용 단위 |
|---|---|
| P-G3 | 모든 S/P에서 제목과 소속 범위를 확인한다. |
| P-G4 | 모든 S/P에서 승인된 같은 핵심을 유지한다. |
| P-G5 | 모든 S/P와 설명 문장에서 실제 설명·필수 연결·문장별 역할을 확인한다. |
| ALL-G12 | 전체 플랜에서 조건, 누락·중복·순서·흐름을 확인한다. |

예시:

> S8 / P2 · 메모리 관리
>
> 실제 설명: 체크포인트를 CPU에 읽은 뒤 선택한 증류 경로에 필요한 티처 모듈을 남겨 GPU로 옮긴다. LM만 사용할 때는 이미지 인코더와 텍스트 디코더가 필요하고, ITM을 함께 사용하면 텍스트 인코더와 ITM 헤드도 필요하다.
>
> 근거: M2. 배치: S8의 표시용 소제목 아래. 핵심 기능 소개 다음에 둔다.

<a id="state"></a>
## 상태 · `work/state.md`

빈 state에 승인 완료 예시를 기본값으로 채우지 않는다. 실제 근거가 있는 현재 상태만 다음 표에 기록한다.

| 표 | 필수 열 |
|---|---|
| 산출물 | 단계, 경로, 버전, 선행 버전, 작성 상태 |
| 승인 | 단계, 버전, 범위, 내용, 구조, 진행/완료, 사용자 발언·기록 위치 |
| 자체 체크 | 단계, S/P 또는 전체, 기준 ID, 확인 조건, 상태, 확인 위치·근거, 필요한 수정 |
| 진행 | S/P, 원고 위치, 작성됨, 점검됨, 승인 범위와 대응, 남은 일 |
| 변경 묶음 | 식별명, 기존 결정, 구체적 수정안, 이유, 표현/플랜/스펙 구분, 영향 위치, 승인 상태 |
| 다음 작업 | 미해결 질문·자료, 의존 범위, 계속 가능한 독립 작업, 다음 위치 |

승인 상태는 `미승인 / 부분 승인 / 승인`이다. 현재 사용자의 구체적 지시도 근거로 기록한다. 사용자에게 제시한 파일·버전·범위를 기준으로 승인하며 자료 풀의 내부 후보를 사용자 결정으로 바꾸지 않는다. 한 답변이 내용·구조·진행을 함께 승인하면 같은 근거를 연결한다.

기존 승인된 미변경 범위는 새 버전에 승계됐음을 기록한다. 변경된 범위의 옛 체크를 현재 충족으로 복사하지 않는다. 미해결 사항에는 의존 범위, 계속 가능한 독립 작업, 다음 위치를 함께 둔다.

<a id="figures"></a>
## 그림 메모 · `work/figures.md`

그림이 필요한 경우에만 `work/figures.md`를 쓴다. writing-plan에서는 그림별 소속과 연결 위치, 설명할 것, 전달할 핵심을 기록한다. develop에서는 승인된 핵심을 유지하며 의도·내용·간단한 스케치 구성과 실제 캡션·각주·HTML 본문 위치의 연결을 구체화한다. 사용자가 이미 제공한 그림 세부 텍스트는 원자료로 보존한다. 실제 그림은 생성하지 않는다.

## 최종 원고 · `report.html`

독자가 읽을 원고와 필요한 표·출처·각주·그림 빈자리·캡션, 자체 스타일을 담는다. 작업용 승인·체크 로그는 work에 둔다. develop에서는 D-G345로 승인된 제목·핵심·설명·근거·조건의 보존을 모든 S와 소제목·본문·연결에서 확인하고, 원고 작성 기준 G6-1~G7-4와 ALL-G12를 함께 적용한다.
