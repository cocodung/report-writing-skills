# 보고서 작성 스킬 설계 · 논의 초안

기록일: 2026-09-09

최근 갱신: 2026-09-10 · 그룹 6·7의 작성 지침·통과 조건과 적용 사례 구체화

현재 대화에서 합의한 용도와 작업 흐름을 보존하는 설계 기록이다. 실제 SKILL.md 구현과 설치는 아직 진행하지 않았다. 아래의 ‘확정된 방향’과 ‘후속 결정’을 구분한다.

## 0. 문서 구성과 구현 계획으로의 인계

이 문서는 `report-writing-skill/` 개발 저장소의 `docs/superpowers/specs/`에서 관리한다. 사용자가 승인한 폴더 분리·로컬 Git 구성을 반영하여 기존 네 문서를 함께 이동했다. 저장소의 현재 상태와 다음 작업은 [README](../../../README.md)에 정리한다. 예시의 원자료는 상위 보고서 작업 폴더에 연결하며, 스킬 실행 시의 산출물 저장 구성은 별도 후속 결정으로 남긴다.

같은 폴더의 네 문서는 아래 역할을 가진다. 스킬 구현의 기준 스펙은 이 문서 하나이며, 나머지는 예시·판단 근거·과거 검토 기록이다.

이후 Superpowers의 `writing-plans`가 만드는 것은 **이 작성 스킬을 제작하는 구현 계획**이다. 스킬 실행 중 단계 3에서 만드는 **보고서 라이팅 플랜(P 항목)**과 구별한다. 보고서 집필 단계를 수행할 때 Superpowers의 소프트웨어 구현 계획 형식을 자동으로 적용한다는 뜻이 아니다.

구현 계획의 `Spec` 항목은 이 설계 문서를 가리키고, 예시·작업 메모·검토 기록은 역할이 표시된 보조 참조로 연결한다. 계획의 각 작업에는 관련 스펙 조항, 만들거나 수정할 파일, 들어갈 지침·양식의 실제 내용, 결과를 확인할 방법을 대응시킨다. 계획은 `docs/superpowers/plans/` 아래의 한 문서로 작성하는 방향이며, 네 참조 문서마다 별도 구현 계획을 만들지 않는다.

계획 작성 전에는 후속 사용자 의견이 기준 스펙에 반영되어 있는지 확인하고, §6의 후속 결정과 체크리스트 후보 중 이미 합의된 내용은 정리한다. 실제로 미정인 작성 정책은 미정 상태를 드러내며 구현 계획 작성자가 임의로 확정하지 않는다. 최신 사용자 지시가 문서와 다르면 그 지시를 반영해 기준 스펙을 갱신하고, 보조 문서의 예전 설명을 우선하지 않는다.

## 1. 확정된 방향

### 용도와 범위

자료 또는 기존 초안과 작성 조건을 입력받아, 핵심을 선택하고 필요한 설명을 조직하여 실제 원고를 작성하거나 재작성한다.

적용 범위는 논문을 포함한 보고서 전반이다. 우선 결과보고서에 적용하는 방식을 구체화한다. 기존 초안을 수정할 때는 잘된 설명을 살리고 핵심을 가리는 내용과 배치를 고친다.

이번 설계와 구현의 대상은 작성 스킬 하나다. 별도의 피드백 스킬은 후속 작업으로 보류한다. AGENTS.md를 통해 이 스킬을 자동으로 실행하는 기능은 넣지 않는다.

### 입력

- 글감: 실험 기록, 메모, 관련 자료, 기존 초안 등 사용자가 제공한 작성 재료.
- 작성 조건: 목적, 독자, 문서 유형, 필수 형식, 표현 방식, 사용자가 강조하려는 내용.
- 대화에서 보완한 의도: 이미 주어진 자료로는 알 수 없는 강조점과 설명 방향.

### 사전 검토

긴 원고를 작성하기 전에 목적·독자·형식과 전체 구성을 담은 짧은 작성안을 사용자가 검토할 수 있게 한다.

지침을 구체화하는 현재 설계 대화는 그룹 1·2 검토와 승인, 그룹 3·4·5 검토와 승인, 그룹 6·7 논의 순서로 진행한다. 실제 스킬 실행 시에는 사용자가 추가로 요청한 단계 내부의 내용·구조 승인, 자체 체크리스트, 단계 전환 승인을 적용한다. 구체적인 규칙은 3절에 기록한다.

## 2. 네 단계와 그룹의 적용

그룹은 단계별로 판단의 목적과 깊이를 달리해 적용한다. 단계 1에서 작성 조건과 큰 흐름을 정하고, 단계 2에서 섹션별 핵심을 선별하며, 단계 3에서 그 핵심을 설명할 문장과 순서를 구축한다. 단계 4에서는 앞서 승인된 내용을 보존하면서 문단과 표현 형식으로 구현한다.

### 단계 1. 글감 브레인스토밍

자료와 기존 초안을 읽고, 사용자와 대화하면서 글감을 모은다. 글감뿐 아니라 사용자의 미세한 의도와 강조하려는 내용을 질문하여 확인한다. 목적·독자·문서 형식과 전체 흐름도 함께 구체화한다.

주로 그룹 1·2를 적용하여 목적·독자·문서 형식·표현 방식과 전체 흐름을 정한다. 세부 제목이나 설명 문장을 확정하는 단계는 아니다. 사용할 재료와 전달 의도를 탐색하고, 후속 단계가 따라야 할 작성 조건과 큰 구성 방향을 남긴다.

브레인스토밍 풀은 원자료의 위치와 내용 안내, 대화에서 확인한 설명·선택 이유·강조점을 포함하는 넓은 참조 자료다. 이후 스펙을 짧게 작성해도 원자료와 글감으로 다시 돌아갈 수 있게 연결을 유지한다. 자료의 저장 위치와 구체적인 파일 구성은 후속 구현 설계에서 정한다.

### 단계 2. 스펙시트

스펙에서 정의하는 각 섹션에 제목 하나와 핵심 하나를 대응시켜 작성한다. ‘핵심’은 해당 섹션에서 다룰 하나의 설명 목표 또는 전달 메시지다. “메모리 최적화 방안을 설명한다”처럼 무엇을 설명할 것인지 제시하는 문장도 스펙에 사용할 수 있다. 제목과 함께 읽었을 때 설명할 대상과 범위가 드러나야 하며, 실제 방법과 근거는 라이팅 플랜에서 구체화한다. 여러 독립된 설명 목표를 한 문장에 이어 붙여 형식적으로 핵심 하나로 처리하지 않는다. 이 대응 규칙을 원고에 나타나는 모든 표시용 소제목에 확대 적용하지 않는다.

에이전트가 모든 섹션에 그룹 3·4·5를 반복 적용하여 핵심을 추리고 수정한다. 그룹 3은 제목과 핵심의 대응, 그룹 4는 중심 설명 목표·메시지의 선택과 단일성, 그룹 5는 그 핵심을 설명하고 뒷받침할 자료가 있는지를 점검한다.

그룹 5의 점검은 이 단계에서 상세 설명을 본문으로 작성하라는 뜻이 아니다. 필요한 배경·이유·근거의 유무와 주장 범위를 확인한다. 각 섹션에는 제목과 핵심 아래에 **우선 참조**를 짧게 남긴다. 상세한 설명 후보와 점검 결과는 연결된 작업 기록에 보존한다.

참조 포인터의 최소 내용은 **자료 위치 + 참고할 내용 또는 이유 한 구절**이다. 필요하면 절·쪽·슬라이드·기록 항목 등 관련 부분을 찾을 수 있는 범위를 붙인다. 단순히 폴더 전체를 가리키기보다 해당 핵심을 설명하는 데 도움이 되는 자료로 연결한다. 원자료를 찾기 위한 포인터와 사용자 의도·강조점을 찾기 위한 포인터는 참조 이유에서 역할이 드러나도록 한다.

섹션별 점검 이후에는 문서 전체의 누락·중복·순서를 확인한다. 사용자에게는 작성 조건에 연결된 전체 스펙시트를 제공하며, **제목·핵심·짧은 참조 포인터**를 중심으로 유지한다. 상세 원자료나 섹션별 자체 점검 기록을 사용자 검토물에 반복해서 붙이지 않는다.

스펙시트는 무엇을 말할 것인지 정한다. 사용자가 매 섹션의 내부 점검 과정에 참여하거나 따로 승인할 필요는 없다. 에이전트가 전체 점검을 마친 스펙시트를 제시하면 사용자는 그 산출물의 내용과 구조를 검토한다.

### 단계 3. 라이팅 플랜

라이팅 플랜의 필수 입력은 승인된 스펙시트, 작성 조건·사용자 강조점, 스펙의 포인터로 연결된 자료·설명 기록, 보충할 자료를 찾을 수 있는 브레인스토밍 풀이다. 스펙이 정한 설명 목표를 기준으로 연결된 자료를 먼저 확인하고, 필요하면 브레인스토밍 풀에서 관련 자료를 더 찾아 실제 설명으로 확장한다. 스펙만을 정보원으로 삼거나 포인터만 보고 자료 내용을 추측하지 않는다.

승인 이력이 없는 기존 초안에서 §3.6의 조건을 충족하면, 첫 묶음 검토를 위해 스펙 후보에 대응하는 플랜 후보를 함께 준비할 수 있다. 이는 검토용 후보를 준비하는 예외이며, 스펙이나 플랜이 승인되었다는 뜻은 아니다.

우선 참조는 설명을 시작할 단서이며, 사용할 수 있는 자료를 그 목록으로 한정하지 않는다. 모든 참조 내용을 원고에 넣을 의무도 없다. 최초 플랜 작성에서는 승인된 설명 목표·범위 안에서 자료를 추가로 선택하고 포인터를 보완할 수 있다. 설명 목표·범위 자체가 바뀌거나 이미 승인된 플랜의 필수 설명·근거 의미를 바꾸는 경우에는 해당 단계의 변경 규칙을 따른다. 자료가 추가되거나 포인터가 보완되었다는 사실만으로 별도 승인을 요청하지 않는다.

각 제목과 핵심 아래에 실제 설명 내용을 짧은 문장이나 문장형 항목으로 배치하고 순서를 정한다. 필요한 개념·선택 이유·작동 과정·근거·해석 조건을 해당 핵심에 맞게 선택한다. 예를 들어 스펙의 “메모리 최적화 방안을 설명한다”는 플랜에서 “활성화한 증류 경로에 필요한 티처 모듈만 GPU에 올린다”처럼 실제 방안으로 구체화한다. 플랜에서 설명 목표나 집필 지시를 반복하는 것만으로 설명의 뼈대를 완성했다고 보지 않는다.

에이전트는 섹션 전체와 그 안의 각 설명 문장에 그룹 3·4·5를 적용한다. 그룹 3은 설명이 제목의 범위를 지키는지, 그룹 4는 설명을 확장한 뒤에도 중심 메시지가 유지되는지, 그룹 5는 필수 설명이 갖춰져 있고 각 문장이 핵심의 이해·근거·해석 범위에 기여하는지 점검한다.

각 설명 문장이 핵심을 직접 반복할 필요는 없다. 정의·예시·조건·앞뒤 연결도 핵심을 이해하거나 판단하는 데 필요한 역할이 있으면 유지한다. 문장 자체의 세련된 표현과 최종 문단 구성은 다음 단계에서 다듬는다.

피규어가 필요한 경우에는 그 그림이 전달할 핵심을 짧게 설명한다. 그림의 실제 생성은 수행하지 않는다.

라이팅 플랜은 독자가 핵심을 이해하도록 무엇을 어떤 순서로 설명할지 정한다. 에이전트가 모든 섹션을 점검한 뒤 섹션 사이의 설명 순서·공백·중복도 확인하고 전체 플랜을 사용자에게 제시한다.

### 단계 4. 글 라이팅

승인된 라이팅 플랜을 실제 원고로 작성한다. 그룹 6·7을 중심으로 지정된 문서 형식과 표현 방식에 맞춰 문단·문장·불렛·표 등의 형태를 선택하고 연결한다.

그룹 3·4·5는 제목의 범위, 승인된 핵심, 필수 설명과 근거가 원고에 유지되는지 확인하는 데 사용한다. 핵심을 매번 새로 추리는 작업을 반복하지 않는다. 문단과 섹션을 이어 읽으며 흐름이 끊기거나 중심이 바뀌지 않았는지 확인한다.

그룹 1의 작성 조건과 그룹 2의 전체 흐름은 계속 적용된다. 표현을 다듬는 과정에서 변경이 필요하면 3.5절의 기준으로 표현 보완, 플랜 변경, 스펙 변경을 구분한다. 문단 분리나 소제목 추가 자체를 이유로 앞 단계의 재승인을 요구하지 않는다.

이 단계에서도 피규어를 생성하지 않는다. 앞 단계의 그림 설명을 바탕으로 해당 그림에 사용할 실제 설명과 각주를 작성한다.

최종 산출물은 작성하거나 수정한 원고와 그림에 사용할 텍스트다.

### 검토 단위의 정의

단계별 산출물이 달라지므로 검토 단위를 다음과 같이 구분한다.

- **섹션:** 스펙에서 제목·설명 목표·범위를 배정한 내용 단위. 여러 문단과 표시용 소제목을 포함할 수 있다. 스펙에서 하위 섹션으로 목표와 범위를 나누어 두었다면 각각 별도 섹션으로 점검한다. 상위 섹션은 하위 목표들을 묶는 역할과 흐름을 점검한다.
- **표시용 소제목:** 기존 섹션 안에서 설명을 읽기 쉽게 묶거나 예고하는 표현상의 구획. 스펙의 별도 목표를 맡는 단위가 아니며 소속 섹션의 목표와 범위를 따른다. 스펙에 별도 행을 만들거나 별도의 ‘핵심 하나’를 요구하지 않는다.
- **설명 문장:** 라이팅 플랜에서 핵심을 이해시키거나 뒷받침하는 역할을 가진 문장 또는 문장형 항목. 최종 원고의 문장 수나 문단 경계를 미리 고정하지 않는다.
- **문단:** 라이팅 단계에서 설명의 한 흐름을 묶어 읽게 하는 표현 단위. 모든 문단에 제목을 붙이거나 섹션의 핵심을 매번 반복하지 않는다.

스펙에서는 섹션, 플랜에서는 섹션과 그 안의 설명 문장, 원고에서는 문단·문장과 섹션 사이 연결을 점검한다. 모든 단계에서 마지막에는 문서 전체의 흐름을 확인한다.

### 섹션과 표시용 소제목의 판정

Markdown의 `##`·`###`, 번호, 글꼴 크기 또는 제목 문구만으로 판정하지 않는다. 같은 ‘메모리 관리’라는 제목도 스펙에서 배정한 역할에 따라 섹션 제목 또는 표시용 소제목이 될 수 있다.

1. 해당 내용이 승인된 어느 섹션의 설명 목표·범위에 속하는지 확인한다. 스펙에 기록되어 있다는 사실만으로 판정을 끝내지 않고 실제 내용의 역할을 비교한다.
2. 그 목표를 풀어 설명하는 기존 하위 주제를 묶는다면 표시용 소제목으로 둘 수 있다. 소속 섹션과의 대응은 작업 기록에서 확인할 수 있게 한다.
3. 기존 목표·범위에 수용되지 않는 설명 목표를 새로 맡기거나, 승인된 핵심·범위를 분리하거나 바꾸면 스펙 변경이다. 제목만 표시용이라고 붙여 이 절차를 건너뛰지 않는다.
4. 목표·범위는 유지해도 이미 승인된 플랜의 필수 설명·근거 의미가 바뀌면 플랜 변경이다. 표시용 소제목인지의 판정과, 그 아래 내용을 바꿔도 되는지의 판정은 별개다.

최초 라이팅 플랜에서 스펙의 목표를 풀어 설명할 하위 주제와 표시용 소제목을 정하는 것은 정상적인 플랜 작성이다. 완성된 전체 플랜으로 검토받는다. 이미 승인된 플랜을 바꾸는 경우에만 그 승인 결정과 비교해 변경 수준을 판단한다.

### 점검 범위와 사례

섹션별 체크리스트의 기준 목록은 스펙의 섹션 목록이다. 표시용 소제목 때문에 독립된 섹션 체크리스트를 늘리지 않는다. 다만 소제목의 표현은 그룹 3·6·7로, 그 아래 설명은 그룹 4·5·6·7로 **소속 섹션의 점검 안에서 모두 확인**한다. 추가된 소제목이나 내용이 어떤 섹션에도 대응하지 않으면 점검을 통과할 수 없다.

스펙의 한 섹션이 ‘선택 가능한 통합 증류기’를 설명하고, 승인된 플랜에 경로 선택·필요한 티처 모듈 적재·이미지 표현 재사용이 이미 포함되어 있다고 가정한다.

| 변경 | 판정과 처리 |
|---|---|
| 기존 설명을 ‘경로 선택’, ‘메모리 관리’, ‘연산 재사용’으로 나누어 표시 | 세 개의 표시용 소제목. 기존 내용과 의미가 유지되므로 표현 보완이며 별도 승인 없이 작성한다. |
| ‘메모리 관리’ 아래에 플랜에서 빠져 있던 필수 전송 과정 설명을 새로 추가 | 같은 섹션의 목표를 설명하더라도 필수 설명이 달라지므로 플랜 변경. 표시용 소제목이라는 이유로 자율 변경으로 처리하지 않는다. |
| 같은 자리에서 목표를 ‘통합 증류기 구현 방식’에서 ‘장치별 배포 적합성 평가’까지 확장 | 새로운 설명 목표·범위이므로 스펙 변경. 제목의 형식과 관계없이 수정안을 묶어 검토받는다. |

반대로 스펙 단계부터 ‘메모리 관리’를 별도의 목표·범위를 가진 하위 섹션으로 배정했다면 그 항목은 실제 섹션이다. 이후 문서에서 어떤 크기로 표시하든 해당 섹션의 핵심과 참조 포인터, 점검 대응을 유지한다.

### 에이전트 점검과 사용자 검토의 구분

에이전트가 모든 섹션의 점검과 수정을 먼저 마친다. 단일 에이전트가 전체 범위를 순회하는 방식으로 설계하며, 이를 별도 피드백 스킬이나 섹션별 서브에이전트 실행으로 해석하지 않는다.

사용자의 기본 검토 대상은 단계 전체 산출물이다. 스펙 단계는 전체 스펙시트, 플랜 단계는 전체 라이팅 플랜을 제시한다. 내용 승인과 구조 승인은 같은 산출물을 검토하는 두 기준이며, 섹션마다 별도의 사람 승인을 반복하는 절차가 아니다. 사용자가 특정 범위의 분할 검토를 요청한 경우에는 그 범위로 나눈다.

내부 점검으로 해결할 수 없는 자료의 누락이나 의도의 불확실성이 핵심 선택을 좌우하면 그 문제에 한해 사용자에게 질문한다. 점검 기록과 근거 연결은 작업 기록에 보존하고, 사용자에게는 정리된 산출물을 제공한다.

## 3. 승인과 자체 점검

### 3.1 사용자가 승인한 진행 원칙

각 단계 내부에서 에이전트가 해당 단계의 점검을 마친 뒤, 단계 전체 산출물의 내용과 구조를 검토받고 승인받는다. 섹션이 구성되는 스펙 단계부터는 모든 섹션의 점검을 포함한다. 섹션별 사람 승인을 기본으로 요구하지 않는다. 다음 단계로 넘어가기 전에는 해당 단계 전체의 자체 체크리스트를 충족하고 단계 전환 승인을 받는다. 최종 글 라이팅 단계에서는 다음 단계 전환 대신 원고의 완료 승인을 받는다.

승인 이력이 없는 기존 초안의 첫 진입에서는 §3.6에 따라 작성 조건·스펙·플랜 후보를 함께 준비하고 한 번에 검토받을 수 있다. 이 경우에도 각 단계의 자체 점검과 내용·구조·진행 승인 범위는 따로 확인한다. 일반적인 신규 집필에는 위의 단계별 순서를 적용한다.

단계 전환에는 다음 조건이 모두 필요하다.

- 현재 산출물의 내용이 사용자에게 승인되었다.
- 현재 산출물의 구조가 사용자에게 승인되었다.
- 적용되는 자체 체크리스트가 모두 충족되었다.
- 사용자가 해당 산출물로 단계를 완료하고 다음 단계로 진행하는 것을 승인했다.

자체 점검 통과는 사용자 승인을 대신하지 않고, 부분 승인은 단계 전체 승인을 대신하지 않는다. 미충족 항목이나 미승인 범위가 남아 있으면 현재 단계에서 수정한다. 사용자 의도나 자료가 필요한 항목은 해결할 질문을 구체적으로 제시한다.

이 규칙은 스킬에 명시할 필수 진행 절차다. SKILL.md만으로 시스템 수준의 실행 차단이 보장된다고 표현하지 않는다.

### 3.2 검토와 수정의 순서

1. 해당 단계의 산출물을 준비하고 자체 점검한다. 섹션이 있는 산출물은 에이전트가 모든 섹션을 점검·수정한 다음, 섹션 사이 연결과 문서 전체도 점검한다.
2. 정리된 단계 전체 산출물을 사용자에게 제시해 내용과 구조를 검토받는다. 사용자가 분할 검토를 요청한 경우에만 지정한 범위로 나눈다.
3. 피드백을 반영하고 수정한 부분과 영향을 받는 체크 항목을 다시 확인한다.
4. 현재 버전의 단계 산출물에 대한 내용 승인과 구조 승인을 기록한다. 특정 범위만 승인받은 경우에는 그 범위를 명시한다.
5. 해당 단계에 적용되는 섹션별·전체 체크리스트가 충족되었는지, 단계 전체의 내용과 구조가 승인되었는지 확인한다.
6. 단계 전환 승인을 받고 다음 단계로 진행한다. 글 라이팅 단계에서는 완료 승인을 받는다.

내용과 구조는 구별해 확인하되, 하나의 검토 요청과 사용자 답변에서 함께 승인받을 수 있다. 사용자가 내용·구조와 다음 단계 진행을 명시적으로 함께 승인한 경우 그 승인 범위를 그대로 인정하며 같은 사항을 다시 묻지 않는다. 특정 부분에 대한 긍정적 의견이나 부분 승인을 나머지 범위의 승인으로 확대하지 않는다.

§3.6의 첫 묶음 검토에서는 위 순서의 후보 준비·점검을 각 단계에 수행한 뒤 검토 요청을 합친다. 사용자가 묶음 전체와 집필 진행을 함께 승인하면 단계마다 같은 승인을 다시 요청하지 않는다.

승인은 검토한 산출물의 버전과 범위에 적용된다. 승인 후 변경의 처리 기준은 3.5절을 따른다. 표현 보완은 자체 점검 후 진행하고, 승인된 핵심이나 필수 설명을 바꾸는 실질 변경은 구체적인 변경안을 준비해 묶음으로 검토받는다.

### 3.3 자체 체크리스트의 기록 방식

‘모두 확인했다’는 선언 대신 항목별 점검을 남긴다. 각 항목은 확인할 조건, 상태, 해당 산출물의 위치나 짧은 확인 근거를 가진다. 섹션 단위 항목은 스펙의 모든 섹션에 대해 결과를 남겨 누락 여부를 확인한다. 표시용 소제목과 그 아래 내용도 소속 섹션의 점검 범위에 포함하고 확인 위치를 남긴다. 문서 전체 항목은 별도로 점검한다. 미충족 항목에는 수정할 내용을 기록한다.

체크리스트 통과는 점검을 수행했다는 뜻이 아니라 요구한 상태가 충족되었다는 뜻이다. 누락이나 중복을 발견하고 기록만 남긴 경우에는 미충족이다. 각 항목은 적용 범위·통과 조건·확인 근거를 가지며, “검토했는가”라는 수행 여부만으로 작성하지 않는다.

- 필수 항목을 임의로 삭제하거나 ‘해당 없음’으로 처리하지 않는다.
- 그림 등 조건부 항목은 실제 적용 조건이 없을 때에만 이유를 적어 ‘해당 없음’으로 처리한다.
- 근거가 부족하거나 확인하지 않은 항목을 충족으로 표시하지 않는다.
- 내용·구조가 수정되면 이전 체크 표시를 그대로 유지하지 않고 영향을 받는 항목을 다시 확인한다.
- 점검과 승인 기록은 작업 기록에 남긴다. 보고서 본문에는 집필 과정의 승인 상태나 체크 기록을 넣지 않는다.

### 3.4 단계별 점검 내용 초안

다음은 체크리스트의 내용 후보다. 필수 점검 절차 자체는 합의되었으며, 각 항목의 세부 기준은 그룹별 지침과 함께 구체화한다.

| 단계 | 점검할 내용 |
|---|---|
| 글감 브레인스토밍 | 목적·독자·형식·표현 방식이 정리되어 있는가. 제공된 글감을 파악했는가. 사용자의 강조점과 의도가 기록되어 있는가. 스펙 작성을 좌우하는 미해결 질문이 남아 있지 않은가. |
| 스펙시트 | 모든 섹션에서 제목과 핵심이 대응하는가. 독립된 여러 핵심을 하나로 묶지 않았는가. 필요한 설명과 근거가 참조할 자료에 있고 그 위치가 연결되어 있는가. 상세 자료는 작업 기록에 보존하면서 스펙은 짧게 유지되는가. 필요한 설명 목표의 누락과 불필요한 중복이 없고, 전체 순서가 작성 목적과 이해의 선후관계에 맞는가. |
| 라이팅 플랜 | 스펙에서 배정한 모든 섹션의 목표·범위가 플랜에 대응하는가. 표시용 소제목과 설명은 소속 섹션에 대응하는가. 각 설명 문장에 실제 내용이 있고 핵심의 이해·근거·해석 조건·필수 연결 중 역할을 가지는가. 선정한 필수 설명이 모두 반영되고 역할 없는 반복이 해소되었는가. 문장과 섹션의 선후관계가 맞는가. 필요한 그림의 중심 메시지가 적혀 있는가. |
| 글 라이팅 | 제목의 범위와 승인된 핵심·필수 설명이 원고에 유지되는가. 문단과 섹션을 이어 읽었을 때 흐름이 유지되는가. 그룹 6·7의 문단·용어·표현 형식이 작성 조건에 맞는가. 중요한 근거와 해석 조건이 유지되었는가. 그림 생성 없이 필요한 설명·캡션·각주를 작성했는가. |

### 3.5 라이팅 중 변경 처리 규칙

사용자가 예시와 함께 검토하고 승인한 규칙이다. 변경의 크기, 문장 수, 제목의 추가 여부가 아니라 **승인받은 결정의 의미가 달라지는지**로 구분한다. 앞 단계가 영향을 받는 경우에도 전체 브레인스토밍을 처음부터 반복하지 않는다.

#### 변경의 세 수준

| 구분 | 판단 기준 | 예시 | 처리 |
|---|---|---|---|
| 표현 보완 | 섹션의 핵심·범위, 필수 설명과 근거의 의미, 설명의 논리적 의존관계를 유지한다. | 문단 분리·병합, 줄글의 불렛 전환, 같은 내용을 묶는 소제목 추가, 의미를 보존한 제목 수정, 핵심 문장의 선제시, 필요한 연결 문장·용어 풀이·출처 표기 보완. | 에이전트가 수정하고 관련 체크 항목을 확인한다. 별도 재승인 없이 집필을 계속하며 단계 전체 원고 검토에 포함한다. |
| 라이팅 플랜 변경 | 섹션의 핵심은 유지하지만 필수 설명의 추가·삭제, 근거가 뒷받침하는 내용, 설명의 논리적 의존관계가 달라진다. | 핵심 이해에 필요한 작동 원리를 새로 추가, 필수 실패 분석을 본문에서 제외, 결론을 설명하는 비교 근거를 다른 지표로 교체. | 해당 플랜과 그에 의존하는 원고의 변경안을 준비해 묶음으로 승인받는다. 기존 스펙의 핵심이 유지되는지 확인한다. |
| 스펙 변경 | 섹션의 핵심·설명 범위·역할이나 문서의 주요 논리 구성이 달라진다. | 중심 기여를 바꿈, 독립된 주장을 가진 섹션을 추가·제거, 기존 핵심을 둘로 분리, 주요 섹션 순서를 바꿔 문서의 설명 경로를 변경. | 스펙 수정안과 관련 플랜의 변경 범위를 함께 제시한다. 변경 승인을 받은 뒤 영향을 받는 설명과 원고를 갱신한다. |

문서 목적·독자·필수 형식 자체를 바꿔야 한다면 그룹 1·2의 작성 조건도 함께 변경 대상으로 제시한다. 변경되지 않은 조건과 승인된 내용은 유지한다.

#### 경계를 판단하는 기준

- 제목을 추가했더라도 기존 내용을 읽기 쉽게 묶는 표시이고 독립된 핵심이나 새로운 설명 범위를 만들지 않으면 표현 보완이다. 스펙의 섹션 목록은 그대로 유지하며, 표시용 소제목과 그 내용은 소속 섹션의 점검에 포함한다. 제목 추가와 함께 필수 설명이나 근거를 바꾸었다면 그 내용 변경은 별도로 판정한다.
- 같은 설명을 읽기 쉽게 재배열하는 일은 표현 보완이다. 전제·원인·방법·결과의 관계를 바꾸거나 새로운 필수 단계를 넣으면 플랜 변경이다.
- 용어 풀이와 짧은 예시가 이미 승인된 개념을 이해시키고 새 주장이나 근거를 도입하지 않으면 표현 보완이다. 빠진 필수 작동 원리나 새 비교 근거를 보충해야 한다면 플랜 변경이다.
- 출처 서식을 고치거나 이미 사용한 근거의 위치를 명확히 하는 것은 표현 보완이다. 근거 자료나 비교 기준을 바꿔 설명의 의미가 달라지면 플랜 변경이며, 그 결과 핵심 주장도 바뀌면 스펙 변경이다.
- 필수 근거를 삭제하거나 해석에 필요한 조건을 숨기는 일을 단순한 분량 축소·가독성 개선으로 처리하지 않는다.

#### 변경안을 검토받는 방식

1. 에이전트가 변경 이유와 영향을 확인하고, 검토할 수 있는 수정안을 준비한다. ‘이 부분을 바꿔도 되는가’라는 추상적인 요청만 제시하지 않는다.
2. 관련 변경들을 한 묶음으로 모은다. 각 항목에는 기존 내용, 제안 내용, 변경 이유, 영향받는 스펙·플랜·원고의 위치를 적는다. 원고와 함께 요약·결론·그림 설명·각주·상호 참조에도 영향이 있는지 확인한다.
3. 사용자에게 변경된 전체 맥락과 수정 부분을 제시하고, 그 변경 묶음에 대한 내용·구조와 진행 승인을 받는다. 섹션별로 승인을 반복 요청하지 않는다. 이미 승인된 미변경 범위를 다시 승인받지 않는다.
4. 승인 대기 중에는 영향을 받지 않는 집필과 점검을 계속할 수 있다. 변경에 의존하는 부분은 검토용 수정안으로 준비할 수 있지만, 승인된 원고로 확정하거나 다음 단계로 넘기지 않는다.
5. 승인 후 스펙·플랜·원고의 대응을 갱신하고 영향을 받는 체크 항목과 문서 전체 흐름을 다시 확인한다. 새 버전의 내용과 구조가 이번 승인 범위에 포함되었는지 기록한다.

승인은 제시한 변경 묶음에 적용된다. 이후 발견한 다른 실질 변경에 대한 포괄 승인으로 확대하지 않는다. 사용자가 이미 구체적인 변경을 지시했다면 그 지시가 제공한 승인 범위를 인정하고 같은 허가를 반복 요청하지 않는다.

자료 확인 결과 기존 주장을 유지할 수 없거나 중요한 근거가 없으면 해당 부분을 통과 처리하지 않는다. 확인된 문제와 근거에 맞는 수정안을 제시하고, 그에 의존하는 부분의 확정은 보류한다.

### 3.6 기존 초안의 진입과 중단 작업의 재개 · 첫 묶음 검토 조건 확정, 나머지 논의안

기존의 승인·변경 원칙을 진입 상황에 적용한다. 아래의 ‘승인 이력이 없는 초안의 첫 검토’ 조건은 사용자와 합의했으며, 나머지 진입·재개 세부 기준은 검토안이다. 가장 뒤 단계의 파일이 있다는 이유로 진입점을 정하지 않고, 확인된 작성 조건·승인 범위·남은 작업을 기준으로 정한다. 이미 제공된 조건과 자료, 좋은 문단은 재사용한다.

| 입력 상황 | 에이전트가 먼저 확인할 내용 | 진입과 검토 범위 |
|---|---|---|
| 원자료만 있음 | 목적·독자·형식·강조점·범위를 현재 지시와 자료에서 채운다. 작성 방향을 좌우하는 누락만 질문한다. | 단계 1에서 시작한다. 작성 조건과 큰 흐름을 검토받은 뒤 스펙을 작성한다. |
| 기존 초안만 있고 승인된 스펙·플랜이 없음 | 초안을 읽어 작성 조건, 섹션별 핵심, 필수 설명과 순서를 후보로 추출한다. 사용자 지시로 확인한 의도와 초안에서 추정한 의도를 구별하고, 유지할 문단과 바꿀 결정을 연결한다. | 초안은 글감이며, 추출한 스펙·플랜 후보는 아직 승인된 결정이 아니다. 기존 초안과 현재 지시에서 작성 방향이 충분히 확인되면 아래 조건에 따라 첫 검토를 한 묶음으로 받는다. 방향이 불명확하면 핵심 의도를 먼저 확인한다. |
| 승인된 스펙이 있음 | 그 스펙의 버전·승인 범위·작성 조건과 자료 포인터를 확인한다. 플랜 작성 진행도 승인되었는지 확인한다. | 단계 3으로 진입한다. 진행 승인만 확인되지 않았다면 그 부분만 확인하며, 기존 스펙의 내용·구조 승인을 반복하지 않는다. |
| 승인된 플랜과 부분 원고가 있음 | 플랜의 버전·승인 범위·집필 진행 승인을 확인한다. 기존 문단을 플랜 항목에 대응시키고 작성·점검 상태를 구별한다. | 단계 4를 재개한다. 플랜에 맞는 문단은 유지하고 남은 부분을 작성한다. 플랜과 다른 내용은 §3.5의 세 수준으로 판정한다. |

현재 대화에서 사용자가 특정 파일을 가리켜 “승인된 플랜이니 이어서 써라”라고 명시한 것도 유효한 승인·진행 근거다. 옛 대화를 다시 제출하도록 요구하지 않는다. 파일명에 `approved`가 있거나 작업 메모에 근거 없이 ‘승인됨’이라고 적혀 있는 것만으로 승인 사실을 추정하지 않는다.

#### 승인 이력이 없는 초안의 첫 검토 · 확정

사용자는 2026-09-09 대화에서 ‘기존 초안과 현재 지시에서 작성 방향이 충분히 확인되는 경우에 한해 묶음 검토를 적용한다’는 설명에 “오케이 그 조건으로 가자”라고 동의했다. 이 승인은 첫 검토 방식에 대한 결정이며, 아직 만들지 않은 실제 검토물이나 스킬 전체에 대한 승인이 아니다.

기존 초안과 현재 지시에서 목적·독자·형식·강조점·대략적인 범위와 큰 흐름을 정리할 수 있고, 스펙의 핵심 선택을 바꿀 미해결 질문이 없으면 작성 조건·스펙·플랜 후보를 한 묶음의 검토물로 제시한다. 초안에서 추정한 의도는 후보임을 드러낸다. 작성 방향을 바꿀 불확실성이 있으면 해당 의도를 먼저 질문해 확인한 뒤 후보를 확장한다. 방향이 계속 미정이거나 사용자가 단계별 검토를 원하면 작성 조건 → 스펙 → 플랜을 순서대로 검토받는다.

에이전트는 각 단계에 해당하는 내용과 구조의 자체 점검을 모두 수행한다. 검토물은 작성 조건 → 섹션별 핵심 → 실제 설명과 순서의 대응을 보여주며, 기존 초안에서 무엇을 유지하고 무엇을 바꿀지 드러낸다. 사용자가 그 묶음의 내용·구조를 채택하고 집필 진행을 승인하면, 각 단계의 점검과 승인 범위가 충족되었는지 확인한 뒤 단계 4에 진입한다. 하나의 명시적 답변으로 이 승인을 함께 받을 수 있다.

부분 승인은 해당 산출물의 버전과 범위에 남긴다. 예를 들어 작성 조건과 스펙이 승인되고 플랜의 설명 순서만 수정 요청을 받았다면 승인된 조건과 핵심은 유지하고, 플랜 수정안과 영향을 받는 범위만 다시 검토받는다. 수정 결과 조건이나 핵심도 달라진다면 그 영향까지 포함한다. 미승인 범위가 남은 묶음을 전체 승인으로 처리하거나 집필 단계로 넘기지 않는다.

이 방식은 기존 초안의 처음 진입에서 여러 단계의 후보를 함께 준비하는 예외다. 아직 제시하지 않은 설명이나 미해결된 조건까지 승인된 것으로 처리하지 않는다. 원자료만 있는 일반적인 신규 집필의 단계 순서를 자동으로 단축하지 않는다.

#### 최소 재개 기록

작업 기록에는 다음 내용을 남긴다. 실제 파일 이름과 저장 구성은 후속 구현 계획에서 구체화한다.

| 기록할 내용 | 포함할 정보 |
|---|---|
| 현재 작업과 조건 | 대상 문서, 이번 수정 범위, 목적·독자·형식·강조점, 최신 사용자 지시의 위치 |
| 참조 대상 | 자료 풀·스펙·플랜·원고의 위치와 구별 가능한 버전 |
| 승인된 결정 | 산출물 버전과 범위별 내용·구조·진행 또는 완료 승인, 이를 확인할 사용자 발언이나 기록의 위치 |
| 진행 상태 | 어떤 플랜 항목이 작성되었고 점검되었는지, 남은 작업과 다음 시작 위치. 작성됨·점검됨·사용자 승인됨을 구별한다. |
| 미해결 사항 | 필요한 자료·질문·변경안, 영향을 받는 범위, 승인 대기 여부와 그동안 계속할 수 있는 작업 |

재개 시 현재 파일과 승인된 내용이 달라졌다면 변경된 결정만 확인한다. 포인터나 기록이 빠진 경우 필요한 부분을 복원하며, 그 이유만으로 승인된 구조 전체를 다시 설계하지 않는다. 근거 부족이 있는 주장은 그 부분과 의존하는 범위의 확정을 보류하고, 영향을 받지 않는 작업은 계속한다. 이와 별개로 단계 전체의 통과 조건과 승인 상태는 충족해야 한다.

### 3.7 인계 시 남은 경계의 명문화 · 논의안

- **내부 기록과 승인 결정:** 글감의 설명 후보·선택 이유·검토 중 순서는 참고 기록이다. 핵심의 의미나 성립 범위를 좌우하는 조건은 사용자에게 보여주는 스펙의 핵심이나 그에 연결된 짧은 조건으로 드러낸다. 사용자에게 제시하지 않은 내부 후보를 승인된 결정으로 취급하지 않는다.
- **변경 범위와 새 내용:** 변경 범위의 승인은 그 범위의 수정안을 작성할 수 있다는 뜻이다. 이미 제시한 구체적인 수정 내용이나 사용자가 직접 지시한 결정은 그 승인 범위로 인정한다. 아직 제시하지 않은 새로운 설명 결정은 다음 산출물 검토에 묶어 포함한다.
- **브레인스토밍의 종료:** 목적·독자·문서 형식·강조점·대략적인 범위가 정리되고, 사용 가능한 자료와 위치가 파악되며, 스펙의 핵심 선택을 바꿀 미해결 질문이 없어야 한다. 이 작성 조건과 큰 흐름을 사용자에게 제시해 내용·구조·스펙 작성 진행을 승인받는다. §3.6의 첫 묶음 검토에서는 작성 조건 후보의 점검을 마친 뒤 스펙·플랜 후보를 함께 준비하고, 각 단계의 승인 범위를 묶음 검토에서 확인할 수 있다. 모든 자료를 완전히 읽거나 세부 문장까지 결정하는 것을 종료 조건으로 요구하지 않는다.

## 4. 표현 방식

두 표현 방식은 문서의 핵심을 선별하고 필요한 설명을 조직한다는 공통 기준을 따른다.

| 사용자 지시 | 작성에 반영할 방향 |
|---|---|
| 가독성을 중시하라 | 결과보고서형을 기본으로 제목·불렛·여백·표 등을 활용한다. 핵심과 보충 설명, 서로 다른 비교 목적이 구별되도록 배치한다. 이미 정해진 논문형·필수 양식이 있으면 그 안에서 가독성을 높인다. |
| 논문형으로 작성하라 | 지정된 양식을 따르며 문단의 핵심을 앞에 두고 설명·근거·해석을 연결한다. 문단 간 논리적 진행이 드러나도록 작성한다. |

문서별로 선택한 표현 방식은 작성 조건에 남겨 이후 단계에서도 유지한다.

### 4.1 그룹 6·7의 역할과 적용 범위 · 방향 동의, 구체화안 검토

사용자는 2026-09-10 대화에서 그룹 6·7의 요약에 “내용 자체는 괜찮은데”라고 평가하고, 이를 적용·점검 가능한 문장으로 풀어 쓴다는 설명 이후 구체화를 요청했다. 아래는 그 방향과 기존 피드백·첫 연결 예시를 바탕으로 다듬은 검토안이다. 구체화된 문구에 대한 피드백은 항목별 승인 없이 한 묶음으로 받는다.

그룹 6은 문단·문장·용어로 설명을 연결하는 기준이고, 그룹 7은 그 설명의 관계와 중요도를 형식으로 드러내는 기준이다. 두 표현 방식은 핵심·근거·필수 조건을 보존한다는 공통 기준을 따른다. ‘작성 지침’은 작성 중 수행할 행동이고, ‘통과 조건’은 그 결과가 갖춰야 할 상태다. 작성 스킬 자체의 점검에 같은 기준을 사용하며, 별도 피드백 스킬의 구현은 후속 작업으로 둔다.

이 기준은 글 라이팅 단계에서 집중 적용한다. 스펙과 플랜에도 의미와 관계를 알아볼 수 있는 표현이 필요하지만, 최종 원고의 문단·서식을 앞 단계에 모두 요구하지 않는다. 승인된 핵심이나 필수 설명의 의미를 바꾸어야 한다면 §3.5의 변경 규칙을 적용한다.

### 4.2 작성 지침과 통과 조건 · 구체화안

| ID | 작성 지침 | 통과 조건 |
|---|---|---|
| G6-1 | 문단이 맡은 설명 흐름의 요점을 앞부분에 두고, 필요한 이유·과정·근거·조건을 이어 쓴다. | 문단 앞부분에서 설명 대상과 요점을 식별할 수 있고, 뒤의 문장들이 같은 설명 흐름에 기여한다. 이해에 필요한 짧은 전제나 앞 문단과의 연결이 요점보다 먼저 올 수 있다. 요점이 이미 분명한 문단은 요약 문장을 추가하지 않고 유지한다. 문단마다 섹션의 핵심을 반복하거나 여러 작동 단계를 각각 독립 문단으로 쪼갤 필요는 없다. |
| G6-2 | 이유·방법·결과·해석의 관계와 설명에 필요한 선후관계를 문장과 문단 사이에 드러낸다. | ‘이것’, ‘해당 방식’, ‘이 결과’가 가리키는 대상을 식별할 수 있고, 독자가 필요한 정의나 중간 과정을 추측하지 않고 다음 설명을 이해할 수 있다. 내용만으로 관계가 분명하면 접속어를 덧붙이지 않아도 된다. ‘따라서’, ‘그 결과’를 추가하여 자료에 없는 인과관계를 만들지 않는다. |
| G6-3 | 원자료에 맞는 정확한 명칭을 일관되게 쓰고, 지정된 독자에게 필요한 용어만 처음 쓰거나 인접한 위치에서 짧게 설명한다. | 명칭만 보고 무엇을 다루는지 구별할 수 있으며, 정확한 ‘출력 토큰 임베딩’을 막연한 ‘정보’로 바꾸지 않는다. 정의는 현재 설명을 이해하는 데 필요한 범위를 갖춘다. 정확성을 이유로 무관한 구현 세부나 이미 충분한 용어 풀이를 추가하지 않는다. 약자는 뜻과 용법을 안내한다. U·M·P 같은 작업용 참조 표기는 자료·플랜에서 유지할 수 있으며 원고의 독자용 출처 표기와 구별한다. |
| G6-4 | 승인된 플랜의 필수 설명을 유지하면서 역할 없는 반복·당연한 부연·작성 과정의 기록을 줄인다. | 압축한 원고에서도 작동 조건·비교 기준·근거·해석 범위와 관측·해석·계획의 구분이 유지된다. 정의·예시·리캡은 없애면 이해나 판단이 끊기는 경우 유지한다. 원고에서 빠진 내용 때문에 다른 작동 방식이나 더 강한 결론으로 읽힌다면 미충족이다. 필수 설명을 삭제하거나 부록으로 옮겨 본문에서 판단할 수 없게 만드는 변경은 §3.5로 처리한다. |
| G7-1 | 정보가 이어지는 설명인지, 병렬 항목인지, 같은 기준의 비교인지 판단한 뒤 작성 형식 안에서 문단·불렛·표를 선택한다. | 문단은 이유·과정의 연결을 읽을 수 있고, 불렛은 병렬 관계와 각 항목의 의미를 알 수 있으며, 비교표는 공통 비교 기준을 확인할 수 있다. 형식 전환 후에도 필요한 설명과 인과관계가 남는다. 관계가 이미 분명한 짧은 문단은 유지한다. 병렬 내용이 있다는 이유만으로 불렛·표 전환을 강제하지 않는다. |
| G7-2 | 주 설명과 보충 설명의 역할에 맞춰 소제목·항목의 소속과 깊이를 정한다. | 표시용 소제목은 소속 스펙 섹션에 대응하고, 나란히 둔 같은 수준의 구획은 같은 상위 내용에 직접 속한다. ‘메모리 관리’와 ‘전체 역할 요약’처럼 맡는 역할이 달라도 같은 수준에 둘 수 있다. 섹션 전체 요약을 특정 하위 주제 아래에 잘못 묶지 않는다. 필수 조건은 해당 주장과 함께 읽고 찾을 수 있으며, 부연처럼 배치되어 주장의 성립 범위가 가려지지 않는다. |
| G7-3 | 핵심 메시지와 비교 목적에 맞춰 문장 배치·제목·굵기·여백 등으로 강조의 우선순위를 정한다. | 독자가 핵심과 보충 내용을 구별할 수 있고, 모든 문장이 같은 강도로 강조되지 않는다. 수치의 강조는 비교 대상·지표의 방향·실제 값에 맞으며, 해석을 바꾸는 조건도 함께 읽힌다. 특정 색상이나 소제목·불렛 개수, 반드시 하나만 강조하는 규칙은 요구하지 않는다. |
| G7-4 | 표·그림마다 전달할 메시지와 해석에 필요한 대상·조건·출처를 연결하고, 피규어의 텍스트와 삽입 자리를 준비한다. | 제목·인접 본문·캡션·각주를 함께 읽으면 설명 또는 비교 대상과 필요한 단위·조건·출처를 확인할 수 있다. 그림은 생성하지 않는다. 플랜에는 중심 메시지를 두고, 라이팅에서는 실제 설명·캡션·각주와 삽입 자리를 준비한다. 의도·내용·간단한 스케치 구성은 연결된 제작 메모로 남긴다. 아직 제작하지 않은 그림이나 확보되지 않은 검증 결과가 있는 것처럼 쓰지 않는다. |

문장 수·문단 길이·불렛 개수의 고정 수치를 통과 기준으로 삼지 않는다. 실패·개선 과정을 설명하는 절에서는 해결 방향과 그 의미를 먼저 제시하고 과정을 연결하되, 계획한 해결책과 실제로 확인한 결과를 구별한다. 모든 문단을 같은 ‘목표·문제·성과’ 틀로 반복하지 않는다.

필수 설명은 문구나 문장 수가 아니라 의미로 보존한다. 문장을 합치거나 짧게 써도 작동 조건·비교 기준·근거·해석 범위를 동일하게 확인할 수 있으면 표현 보완이다. 그 정보 자체가 삭제되거나 의미가 달라지는 경우에 §3.5의 변경 규칙을 적용한다.

### 4.3 짧은 지시에 따른 적용 · 구체화안

| 사용자 지시 | 그룹 6·7의 적용 방식 | 확인할 차이 |
|---|---|---|
| 가독성을 중시하라 | 결과보고서형에서는 핵심을 먼저 보이고, 관계에 맞는 소제목·불렛·여백·표를 활용한다. 연결된 이유·과정을 설명하는 문단은 유지한다. | 훑어보아도 핵심과 하위 설명의 관계를 알 수 있고, 이어 읽으면 설명이 끊기지 않는가. |
| 논문형으로 작성하라 | 지정된 양식 안에서 본문은 문단 중심으로 구성한다. 각 문단의 핵심을 앞에 두고 이유·근거·해석을 연결하며, 다음 문단의 설명으로 자연스럽게 이어지게 한다. 비교에 필요한 표·그림은 양식에 맞게 사용한다. | 줄글에서도 각 문단의 요점과 문단 사이의 논리적 진행을 알 수 있는가. |

표현 방식은 작성 조건에 저장한다. 이미 논문형이나 필수 양식이 정해져 있다면 ‘가독성을 더 높여라’는 후속 요청은 그 양식 안에서 적용한다. 별도의 형식 변경 지시가 없는데 결과보고서형으로 바꾸지 않는다. 두 방식의 차이를 설명량이나 정확성의 차이로 해석하지 않는다.

짧은 지시 하나로 해당 형식의 작성과 자체 점검에 같은 기준을 적용한다. 사용자가 매번 G6·G7 항목을 다시 나열할 필요는 없다. 결과보고서형에서는 핵심과 하위 설명의 배치를 먼저 훑고 이어 읽기를 확인한다. 논문형에서는 문단별 요점과 문단 사이의 연결을 중심으로 이어 읽기를 확인한다. 두 방식 모두 G6-1~G7-4 중 적용되는 조건을 점검한다.

### 4.4 동일한 내용을 두 방식으로 표현한 짧은 예시 · 검토안

자료는 [통합 증류기 연결 예시의 P2](2026-09-09-integrated-distiller-writing-example.md)다. 기존 섹션 S8의 메모리 관리 설명 일부를 비교하며, 새로운 설명 목표를 가진 섹션을 추가하는 예시는 아니다.

#### 결과보고서형

**필요한 티처 모듈만 GPU에 적재한다.** 체크포인트를 CPU에서 읽은 뒤, 선택한 증류 경로에 필요한 모듈을 남겨 GPU로 옮긴다.

- **LM만 사용:** 이미지 인코더와 텍스트 디코더를 적재한다.
- **LM과 ITM 사용:** 여기에 텍스트 인코더와 ITM 헤드를 추가로 적재한다.

#### 논문형

티처는 선택한 증류 경로에 필요한 모듈만 GPU에 적재하도록 구성하였다. 체크포인트를 CPU에서 읽은 뒤 필요한 모듈을 선별해 GPU로 옮겼으며, LM만 사용할 때는 이미지 인코더와 텍스트 디코더를 적재하였다. ITM을 함께 사용하는 경우에는 텍스트 인코더와 ITM 헤드를 추가로 적재하였다.

두 표현은 CPU 로드 후 모듈을 선별한다는 순서와 경로별 모듈 구성을 동일하게 유지한다. 결과보고서형은 선택지의 차이를 불렛으로 드러내고, 논문형은 같은 비교를 연결된 문장으로 설명한다. 실제 스킬에서 두 버전을 항상 함께 출력하도록 요구하는 것은 아니다.

#### 경계를 확인하는 짧은 수정 사례

아래의 미충족 표현과 배치는 판정 설명을 위해 의도적으로 만든 사례다. 실제 원고에서 발견한 오류 목록이 아니다. 수정 방향은 [연결 예시의 P3·P5와 원고](2026-09-09-integrated-distiller-writing-example.md)에 근거한다.

| 적용 기준 | 미충족 예 | 수정 방향과 통과 이유 |
|---|---|---|
| G6-3 · 정확한 용어 | “인코더의 특징을 여러 경로가 활용한다.” | “티처 이미지 인코더의 출력 토큰 임베딩을 활성화된 증류 경로에서 공유한다.”로 대상을 특정한다. 해당 과정의 작동 범위는 다음 사례처럼 함께 설명한다. |
| G6-4 · 압축 후 조건 보존 | “계산한 임베딩을 학습 중 계속 재사용한다.” | “같은 학습 step에서 계산한 출력 토큰 임베딩을 활성화된 증류 경로에서 공유한다. 다음 step에서는 새 입력을 다시 인코딩한다.”로 범위를 유지한다. 짧아졌다는 이유로 step 간 재사용처럼 읽히면 통과하지 않는다. |
| G7-2 · 설명의 소속 | 세 증류 경로 전체의 역할 요약표를 ‘계산 재사용’ 소제목 아래에 둔다. | 표를 같은 수준의 ‘증류 경로별 역할 요약’ 아래에 두어 섹션 전체를 정리하도록 한다. 같은 내용을 재배치하는 표현 보완이며, 새 스펙 섹션을 요구하지 않는다. |

### 4.5 자체 점검에 반영하는 방식 · 구체화안

1. **대조할 내용 확인:** 작성 조건과 승인된 스펙·플랜에서 섹션의 핵심, 필수 설명·근거·조건, 설명 순서를 확인한다.
2. **섹션별 작성·수정:** 모든 스펙 섹션에 G6-1~G7-4의 해당 조건을 적용한다. 표시용 소제목과 그 아래 문단·불렛·표·그림 텍스트도 소속 섹션에서 확인한다. 변경이 §3.5의 플랜·스펙 변경에 해당하면 구체적인 수정안을 준비한다.
3. **수정 후 재점검:** 각 기준에 대해 섹션·ID·상태·확인 위치와 짧은 근거를 기록한다. 미충족 항목에는 필요한 수정을 남기며, 고친 뒤 영향을 받는 기준을 다시 점검한다.
4. **전체 흐름 확인:** 선택한 표현 방식으로 문단과 섹션을 이어 읽어 설명의 공백·불필요한 중복·논리적 비약이 해소되었는지 확인한다. 표현을 나누거나 합친 뒤에도 승인된 핵심과 필수 설명이 유지되어야 한다.

상태는 §3.3에 따라 충족·미충족·이유가 있는 해당 없음으로 기록한다. 발견한 누락·불명확한 지시 대상·잘못된 위계를 수정하지 않은 채 통과 처리하지 않는다. 표·그림이 없는 경우 그 조건부 부분만 해당 없음으로 처리하고, 설명 관계·용어·핵심 보존의 공통 기준은 계속 적용한다. 미해결 승인·자료 의존 사항은 해당 범위를 통과시키지 않고 작업 기록에 연결한다.

점검은 에이전트가 수행하고, 사용자는 정리된 단계 전체 원고와 필요한 변경 묶음을 검토한다. 문단별 승인이나 그룹 6·7 전용 승인 단계를 추가하지 않는다. 점검 ID와 기록은 작업 기록에 두고, 원고에는 독자에게 필요한 내용과 표·그림 텍스트를 제공한다.

## 5. 지침을 구체화할 그룹

| 그룹 | 역할 |
|---|---|
| 1. 목적·독자·문서 형식 | 작성 조건을 정한다. |
| 2. 전체 구성과 흐름 | 각 부분의 역할, 순서와 경계를 정한다. |
| 3. 제목과 소제목 | 각 구획의 대상과 설명 목적을 드러낸다. |
| 4. 핵심 추출과 강조 | 문서와 각 절의 중심 설명 목표·전달 메시지를 정한다. |
| 5. 설명과 근거 | 핵심을 이해하고 판단하는 데 필요한 내용을 선택한다. |
| 6. 문단·문장·용어 | 선택한 내용을 정확하고 연결된 언어로 작성한다. |
| 7. 표현 형식과 위계 | 정보의 관계에 맞는 형식과 강조 수준을 선택한다. |

이 그룹들은 네 단계에서 사용하는 작성 기준이다. 독립된 일곱 개의 실행 단계를 뜻하지 않는다. 같은 그룹도 단계별 역할이 다르며, 적용 방식은 2절에 정의한다. 세부 규칙은 이어지는 설계 대화에서 정제한다.

## 6. 후속 결정과 제안

### 비판적 검토 후 확정된 수정 방향

- 스펙은 무엇을 설명할 것인지 짧게 정하고, 라이팅 플랜은 이를 실제 설명 내용으로 확장한다. 설명 목표형 문장은 스펙에 허용하며, 플랜에서는 그 목표의 반복으로 끝내지 않는다.
- 플랜은 승인된 스펙뿐 아니라 작성 조건·강조점과 연결된 자료·설명 기록을 함께 참조한다. 참조할 자료의 범위는 짧은 스펙보다 넓다.
- 스펙에 짧은 참조 포인터를 두어 핵심과 원자료·설명 기록을 연결한다. 스펙은 간결하게 유지하면서 브레인스토밍 풀의 자료에 접근할 수 있게 한다.
- 체크리스트는 점검 수행 여부가 아니라 누락·중복 등 문제가 해소된 상태를 기준으로 판정한다.

### 차례대로 논의할 항목

1. **자료의 축적과 인계:** 브레인스토밍 풀을 보존하고 스펙에 참조 포인터를 두는 방향을 반영했다. 이후 플랜은 두 자료를 함께 참조한다.
2. **의미상 섹션과 표시용 소제목:** 설명 목표를 배정한 스펙 단위와 그 안의 표현 구획으로 구분하고, 표시용 소제목의 내용도 소속 섹션에서 점검하는 방식에 사용자가 동의했다.
3. **실제 예시:** 아래의 예시 보완 계획에 따라 [통합 증류기 연결 예시 v0.1](2026-09-09-integrated-distiller-writing-example.md)을 작성했다. 사용자는 원고가 원하는 의도로 나왔다고 평가했다. 처음에는 플랜이 읽기 어렵다고 했으나 해설 후 이해했으며 U·M·P 같은 참조 표기를 유지해도 좋다고 밝혔다. 예시 첫머리에 S=Section, P=Plan, U=User, M=Material 안내를 추가했다.
4. **그룹 6·7 구체화:** 사용자가 요약한 방향을 긍정적으로 평가하고 구체화를 요청했다. §4.1~§4.5의 8개 항목을 작성 행동·통과 조건으로 다듬고, 형식별 적용·수정 사례·자체 점검 순서를 연결했다. 구체화안은 한 묶음으로 검토하며, 항목별 추가 승인을 요구하지 않는다.
5. **남은 인계·승인 조건 정리:** §3.6~§3.7에 기존 초안의 진입·재개, 최소 재개 기록, 내부 기록과 승인 결정의 경계, 미제시 산출물의 승인 범위, 브레인스토밍 종료 기준을 정리했다. 승인 이력이 없는 초안의 첫 검토는 작성 방향이 충분히 확인될 때 한 묶음으로 받으며, 단계별 점검과 승인 범위·부분 승인은 구분하는 조건으로 확정했다. 나머지 세부 논의안은 후속 검토하고, 이후 실행 산출물의 저장 구성·호출 이름을 확정한다.

### 첫 논의: 참조 포인터를 둔 스펙과 자료 확장

사용자의 제안을 반영한 자료 흐름은 다음과 같다. 포인터의 구체적인 표현과 예외는 이 방향 안에서 검토한다.

- 브레인스토밍에서 원자료의 위치와 짧은 내용 안내, 대화에서 얻은 설명·선택 이유, 작성 조건·강조점·제외 범위를 함께 정리한다.
- 원자료를 모두 복사하거나 요약문으로 대체할 필요는 없다. 필요한 원문과 근거로 돌아갈 수 있게 연결한다.
- 스펙은 그 자료에서 작성할 목표와 흐름을 선택하고 섹션별 참조 포인터를 붙인다. 스펙의 글자 수가 줄어도 배경 자료에 접근할 수 있는 연결은 보존한다.
- 라이팅 플랜은 승인된 스펙을 설명 범위의 기준으로 삼고, 우선 참조와 더 넓은 브레인스토밍 풀에서 실제 설명·근거를 선택한다. 전 자료를 매 섹션마다 반복해서 읽는 것을 요구하지 않는다.
- 단계가 진행되면서 실제 원고에 채택하는 내용은 목적에 맞게 좁혀진다. 보존한 자료 자체를 단계마다 삭제하거나 접근할 수 없게 만드는 방식으로 정보량을 줄이지 않는다.
- 이후 대화나 확인으로 자료가 보완되면 기존 기록을 갱신한다. 사용자에게 보여준 승인 결정과 단순한 설명 후보·참고 기록은 구별한다.

### 예시 보완 계획 · 논의안

처음에는 한 문장의 스펙 → 플랜 확장, 섹션·소제목 구분, 세 수준의 변경 판정 예시만 있었다. 같은 글감이 실제 설명과 완성 원고로 이어지는 예시가 없어, 자료 선택·포인터 사용·플랜의 상세도·원고 표현의 연결을 확인하기 어려웠다. 이를 보완한 첫 연결 예시 v0.1을 작성했다.

첫 예시는 실제 보고서의 ‘통합 증류기’ 한 섹션이다. 사용자 피드백은 중심을 경로 선택 기능으로, 하위 설명을 메모리·계산 관리로 정해 두었다. 이 사례로 기본 형태를 보여주고, ITC 개발 과정은 실패·개선의 순서와 본문·부록의 선별을 확인할 보조 사례로 검토한다.

| 예시 구성 | 보여줄 내용 |
|---|---|
| 작은 자료 풀 | 실제 자료 발췌와 위치, 사용자 강조점, 해당 섹션에 사용할 내용과 다른 곳에 둘 내용. 요약만 주지 않고 참조할 원자료를 연결한다. |
| 스펙 | 제목·하나의 설명 목표·우선 참조. 상세 구현 설명은 아직 펼치지 않는다. |
| 라이팅 플랜 | 같은 목표 아래 실제 설명 문장을 순서대로 배치한다. 각 설명에 사용한 자료가 어디인지 확인할 수 있게 하고, 피규어는 중심 메시지만 적는다. |
| 원고 | 같은 플랜을 연결된 문장과 적절한 구획으로 작성한다. 인접 섹션에서 들어오고 다음 섹션으로 이어지는 짧은 부분도 보여준다. 그림은 생성하지 않고 설명·캡션·각주만 작성한다. |
| 짧은 점검·수정 사례 | 목표 문장만 반복한 미충족 플랜 한 항목을 실제 설명으로 고친 뒤, 어떤 기준이 충족되었는지 위치와 함께 보여준다. |

결과보고서형 원고를 먼저 검토하고, 동일한 내용 일부를 논문형으로 표현한 짧은 비교를 그룹 6·7의 구체화에 활용한다. 표현 방식이 달라져도 목표·사실·필수 설명은 유지되어야 한다. 실제 섹션 하나만으로 문서 전체의 구성 품질을 검증했다고 주장하지 않는다.

예시는 설명용 산출물이며 실제 사용자 승인을 받았다고 가정하지 않는다. 사용자가 첫 예시 작성을 승인하여 [검토용 예시 v0.1](2026-09-09-integrated-distiller-writing-example.md)과 [자료 대조·자체 점검 메모](2026-09-09-integrated-distiller-writing-example-notes.md)를 작성했다. 원고의 방향은 긍정적으로 평가되었고, 플랜 해설 후 참조 표기 유지에 동의했다. 이를 스킬 전체나 구현에 대한 승인으로 확대하지 않는다. 보고서 원고를 바로 수정하거나 그림을 생성하는 작업과 구분한다.

#### 사례의 범위와 사용자 피드백 반영

사용자는 예시를 작성한 뒤 직접 피드백과 코멘트를 남기고, 이를 반영하여 사례와 지침을 수정하는 과정을 요청했다. 첫 피드백과 해설 이후의 의견은 작업 메모 §6에 기록했다. 참조 표기를 유지하고 뜻을 처음에 안내하는 방식으로 반영했으며, 실제 설명 내용과 근거 연결을 유지한다.

통합 증류기 한 사례는 기본적인 단계 연결을 확인하는 첫 사례다. 이 사례만으로 실패·개선 과정의 선별, 문서 전체의 흐름, 논문형 표현까지 충분히 검증했다고 보지 않는다. 보완 범위는 다음과 같이 제안하며, 사례 수 자체를 통과 기준으로 삼지 않는다.

- 통합 증류기: 자료 풀 → 스펙 → 실제 설명을 담은 플랜 → 결과보고서형 원고를 연결하여 검토한다.
- ITC의 짧은 보조 사례: 여러 실험과 실패·개선 기록에서 핵심을 선택하고, 필수 설명과 부록으로 옮길 내용을 구분하는 판단을 확인한다.
- 같은 내용의 결과보고서형·논문형 비교: 목표·사실·필수 설명을 유지하면서 문단·소제목·연결 방식을 어떻게 바꿀지 확인한다. 그룹 6·7을 구체화하는 데 사용한다.

섹션 사례에는 앞뒤 연결을 포함하고, 전체 흐름 판단에는 문서의 목차와 섹션별 핵심 배열도 함께 참고한다. 사례 검토 후에도 중요한 판단이 모호하면 그 판단만 확인하는 짧은 추가 예시를 만든다. 첫 사례의 특정 내용이나 구성을 모든 보고서의 필수 형식으로 일반화하지 않는다. 공통 지침으로 정제할 때에는 다른 주제의 짧은 자료에서도 적용 가능한지 확인하며, 필요하면 비교 결과와 해석 조건을 포함한 보조 예시를 사용한다.

예시 검토는 초안 작성 → 사용자 코멘트 → 사례 수정과 지침 후보 갱신 → 수정본 검토 순서로 진행한다. 첫 사례의 피드백으로 기준을 다듬은 뒤 그 기준을 보조 사례에 적용한다. 코멘트별로 관련 위치, 사용자의 의도, 사례에 반영한 수정, 다른 글에도 적용할 수 있는 지침 후보를 연결한다. 특정 실험의 사실 정정이나 해당 문서만의 강조점은 해당 사례·작성 조건에 반영하며, 공통 지침으로 확장할 때는 다른 사례에서도 타당한지 확인한다. 해석이 모호한 코멘트만 사용자에게 확인한다.

수정본에는 주요 변경 전후와 지침에 반영한 내용을 묶어 제시한다. 코멘트마다 별도 승인을 요구하지 않는다. 예시와 지침을 검토하는 현재 설계 과정은 실제 스킬 실행 시 새로운 승인 단계를 추가하는 규칙이 아니다. 예시에 대한 긍정적 평가를 전체 스킬 스펙이나 구현의 승인으로 확대하지 않는다.
