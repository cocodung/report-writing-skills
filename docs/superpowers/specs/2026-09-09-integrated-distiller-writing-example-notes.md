# 통합 증류기 연결 예시 · 자료 대조와 자체 점검

대상: [예시 v0.1](2026-09-09-integrated-distiller-writing-example.md) · 2026-09-09

2026-09-10 이관: 기준 스펙의 판정·수정 사례와 예시 진행·검토 기록을 §3·§5·§6으로 옮겼다. 구→새 대응은 §7에 기록한다.

이 문서는 예시를 작성할 때의 선택과 점검을 기록한다. 보고서 본문이나 추가 사용자 승인 양식이 아니다. 현재 워크스페이스 자료를 읽어 확인했으며, 학습 실행이나 성능 측정은 수행하지 않았다.

§1~§7의 검토·진행 상태는 예시 작성과 스펙 정리 당시의 기록이다. 후속 상태 정정과 호출·출력 지정은 §8~§9에 기록하며, 현재 설계 기준은 스펙 §6을 따른다.

### 자료 간 차이로 적용하지 않은 설명

- [7월 23일 통합 설계](../../../../Distillation_Project/docs/superpowers/specs/2026-07-23-itc-itm-lm-targetmix-merge-design.md)는 ITM target-mix를 다룬다. 현재 예시는 ITM 관계 KD를 사용하므로 당시 손실 결합이나 메서드명을 그대로 옮기지 않았다.
- [7월 23일 인코딩 공유 설계](../../../../Distillation_Project/docs/superpowers/specs/2026-07-23-teacher-forward-dedup-design.md)의 이론적 시간 감소 표현을 현재 통합 구성의 실측 개선으로 사용하지 않았다.
- `online_teacher.py` 7행의 ITM 헤드 해제 주석은 실제 `NEEDS`와 충돌한다. 모듈 판단은 실행되는 자료 구조와 제거 조건에 근거했다.
- 코드가 지원하는 ITC의 γ=0 이후 계산 생략을 최종 실행에서 실제 발생한 것으로 서술하지 않았다. 현재 mainline 설정은 총 20 epoch이며 감쇠 종료는 42 epoch다. 이 예시에 스케줄 세부 설명을 추가하지 않았다.
- 경로 선택은 학습 설정에서 이루어진다. 학습 중 토글을 실시간으로 바꾸는 기능까지 구현했다고 해석하지 않았다.

## 2. 자료 선택과 단계 사이의 대응

| 선택 | 이유 | 반영 위치 |
|---|---|---|
| 경로 선택을 첫 문장으로 이동 | 사용자가 지정한 중심 기여를 먼저 보여준다. | S8 → P1 → 원고 첫 문단 |
| CPU 로드 후 GPU 적재 순서 유지 | 어떤 자원을 줄이는 구현인지 정확히 이해하는 데 필요하다. | M2 → P2 → 메모리 소제목 첫 문단 |
| LM과 LM+ITM 모듈 예시 유지 | 설정 선택이 실제 모듈 구성에 어떻게 반영되는지 구체화한다. | M2 → P2 → 두 불렛 |
| 같은 step과 이미지 인코더 출력이라는 범위 유지 | 무엇을 어디까지 공유하는지 설명한다. | M3 → P3·P4 → 계산 재사용 문단·E-F1 |
| 기본 학습 유지와 세 경로의 정보 비교 유지 | 증류 토글이 학생의 기본 학습까지 제거한다는 오해를 막는다. | M4 → P1·P5 → 첫 문단·마지막 표 |
| 긴 캐시 비교와 분산 통신 설명 제외 | 이번 절의 경로 선택·자원 관리 설명에 필요하지 않다. 관련 원자료와 앞 절에서 다시 확인할 수 있다. | U2·M1 → 자료 풀의 선별 기록 |
| ITM 후보 수·손실식과 개별 실험 결과를 재수록하지 않음 | 방법의 상세 설명은 앞 절에 있고, 여기서는 같은 후보에 대한 정보 전달이라는 역할을 요약한다. | M4 → P5의 표 |
| 결과 비교는 다음 절 도입에 배치 | 구현 설명과 성능 평가의 역할을 구분하고 연결한다. | P6 → §9 도입 예시 |

P2·P3의 자원 관리 소제목과 P5의 역할 요약 소제목은 모두 S8의 구현 설명에 속한다. P4의 그림도 같은 설명 범위다. P6은 S8에서 성능 평가 절로 나가는 연결로, S8에 새 성능 주장이나 평가 결과를 추가하지 않는다.

## 3. 판정과 수정 사례

### 3.1 미충족 플랜을 고치는 예시 · 의도적으로 만든 비교

아래의 ‘수정 전’은 판정 경계를 보여주기 위해 의도적으로 만든 짧은 비교다. 실제 실행 중 자동으로 발견된 오류 이력으로 제시하지 않는다.

**수정 전:** “메모리 최적화 방안을 설명한다.”

**판정:** 스펙의 설명 목표로는 사용할 수 있다. 라이팅 플랜에서는 실제 방안과 필요한 동작 순서가 없어 그룹 5 미충족이다. 자료를 검토했다는 표시만 남겨도 통과하지 못한다.

**수정 후:** “체크포인트를 CPU에 읽은 뒤 선택한 증류 경로에 필요한 티처 모듈을 남겨 GPU로 옮긴다. LM만 사용할 때는 이미지 인코더와 텍스트 디코더가 필요하고, ITM을 함께 사용하면 텍스트 인코더와 ITM 헤드가 추가로 필요하다.”

**재점검:** M2에서 적재 순서와 경로별 모듈을 확인했다. ‘어떤 방안인가’와 ‘선택에 따라 무엇이 달라지는가’에 답하므로 이번 플랜의 설명 기준을 충족한다. 최종 원고에서는 이 내용을 짧은 문단과 두 불렛으로 배치했다.

### 3.2 실제 초안 검토에서 발견하고 수정한 내용

실제 초안 검토에서는 마지막 표가 Markdown상 ‘계산 재사용’ 소제목 아래에 묶이는 문제를 발견했다. ‘증류 경로별 역할 요약’을 같은 깊이의 표시용 소제목으로 추가하여, 표가 통합 증류기 전체를 정리한다는 역할을 드러냈다. 기존 핵심과 표의 내용은 유지했고, P5의 배치 설명과 관련 점검도 갱신했다. P6의 소속 역시 다음 절 도입으로 통일했다.

### 3.3 섹션·표시용 소제목과 변경 수준의 판정 사례

기준 스펙의 구 §2 ‘점검 범위와 사례’에서 옮긴 가정 사례다. 실제 예시에서 이런 변경을 수행했거나 각 단계의 승인을 받았다는 뜻은 아니다.

스펙의 한 섹션이 ‘선택 가능한 통합 증류기’를 설명하고, 승인된 플랜에 경로 선택·필요한 티처 모듈 적재·이미지 표현 재사용이 이미 포함되어 있다고 가정한다.

| 변경 | 판정과 처리 |
|---|---|
| 기존 설명을 ‘경로 선택’, ‘메모리 관리’, ‘연산 재사용’으로 나누어 표시 | 세 개의 표시용 소제목. 기존 내용과 의미가 유지되므로 표현 보완이며 별도 승인 없이 작성한다. |
| ‘메모리 관리’ 아래에 플랜에서 빠져 있던 필수 전송 과정 설명을 새로 추가 | 같은 섹션의 목표를 설명하더라도 필수 설명이 달라지므로 플랜 변경. 표시용 소제목이라는 이유로 자율 변경으로 처리하지 않는다. |
| 같은 자리에서 목표를 ‘통합 증류기 구현 방식’에서 ‘장치별 배포 적합성 평가’까지 확장 | 새로운 설명 목표·범위이므로 스펙 변경. 제목의 형식과 관계없이 수정안을 묶어 검토받는다. |

반대로 스펙 단계부터 ‘메모리 관리’를 별도의 목표·범위를 가진 하위 섹션으로 배정했다면 그 항목은 실제 섹션이다. 이후 문서에서 어떤 크기로 표시하든 해당 섹션의 핵심과 참조 포인터, 점검 대응을 유지한다.

### 3.4 그룹 6·7의 경계를 확인하는 짧은 수정 사례

기준 스펙의 구 §4.4에서 옮긴 검토용 사례다. 아래의 미충족 표현과 배치는 판정 설명을 위해 의도적으로 만든 사례이며, 실제 원고에서 발견한 오류 목록이 아니다. 수정 방향은 [연결 예시의 P3·P5와 원고](2026-09-09-integrated-distiller-writing-example.md)에 근거한다. 표의 마지막 항목은 §3.2의 실제 수정과 같은 배치 유형을 설명하며, 새로 발견한 오류를 뜻하지 않는다.

| 적용 기준 | 미충족 예 | 수정 방향과 통과 이유 |
|---|---|---|
| G6-3 · 정확한 용어 | “인코더의 특징을 여러 경로가 활용한다.” | “티처 이미지 인코더의 출력 토큰 임베딩을 활성화된 증류 경로에서 공유한다.”로 대상을 특정한다. 해당 과정의 작동 범위는 다음 사례처럼 함께 설명한다. |
| G6-4 · 압축 후 조건 보존 | “계산한 임베딩을 학습 중 계속 재사용한다.” | “같은 학습 step에서 계산한 출력 토큰 임베딩을 활성화된 증류 경로에서 공유한다. 다음 step에서는 새 입력을 다시 인코딩한다.”로 범위를 유지한다. 짧아졌다는 이유로 step 간 재사용처럼 읽히면 통과하지 않는다. |
| G7-2 · 설명의 소속 | 세 증류 경로 전체의 역할 요약표를 ‘계산 재사용’ 소제목 아래에 둔다. | 표를 같은 수준의 ‘증류 경로별 역할 요약’ 아래에 두어 섹션 전체를 정리하도록 한다. 같은 내용을 재배치하는 표현 보완이며, 새 스펙 섹션을 요구하지 않는다. |

## 4. 자체 점검

범위는 S8 한 섹션과 인접 절로의 연결이다. ‘충족’은 현재 합의된 기준에 대한 자체 판단이며 사용자 승인과 다르다. 그룹 6·7의 상세 기준과 스킬 전체의 일반성은 이번 사례만으로 확정하지 않는다.

| 단계·그룹 | 통과 조건 | 상태 | 근거 |
|---|---|---|---|
| 브레인스토밍 · 1 | 목적·독자·표현 형식과 사용자 강조점이 자료에 연결되어 있다. | 충족 | 예시 §1의 작성 조건, U1·U2 |
| 브레인스토밍 · 2 | 해당 섹션의 역할과 앞뒤 연결이 정리되어 있다. | 충족 | §1의 앞·현재·뒤 표; 전체 목차는 M1에서 확인 |
| 브레인스토밍 · 1·2 | 이 사례의 핵심 선택을 좌우하는 미해결 자료·의도가 남아 있지 않다. | 충족 | 선택 기능의 우선순위는 U1, 구현은 M2·M3·M4로 확인; 그림 삽입 여부는 검토 후보로 표시 |
| 스펙 · 3·4 | 제목과 하나의 설명 목표가 대응하고, 독립된 성능 평가 목표를 섞지 않았다. | 충족 | S8은 선택·조합하는 통합 구현에 한정 |
| 스펙 · 5 | 목표를 설명할 자료와 의도 기록으로 돌아갈 수 있다. | 충족 | S8의 U1·U2·M2·M3·M4 포인터와 §1의 원문 링크 |
| 플랜 · 3·4 | 모든 하위 설명이 소속 섹션이나 명시된 인접 연결에 대응한다. | 충족 | P1~P5는 S8, P6은 다음 절 도입 |
| 플랜 · 5 | 각 항목에 실제 설명 또는 그림의 핵심이 있고, 필수 동작 조건이 갖춰져 있다. | 충족 | P1 기본 학습 유지; P2 CPU→GPU와 모듈; P3 같은 step의 출력 공유; P5 같은 후보·토큰 위치 |
| 플랜 · 2·5 | 설명 순서와 표의 비교 기준이 일관되며 역할 없는 반복을 해소했다. | 충족 | 중심 기능 → 자원 관리 → 경로별 역할 표; 손실식·실험 이력 재수록 제외 |
| 원고 · 3·4·5 | 플랜의 중심·필수 설명·조건이 표현 과정에서 유지되었다. | 충족 | 원고 첫 문단, 세 표시용 소제목, 표와 캡션의 내용이 P1~P5에 대응 |
| 원고 · 6·7 | 현 작성 조건에 맞춰 핵심을 앞에 두고, 하위 설명과 비교 대상을 구별한다. | 현 합의 기준 충족 | 첫 문장 강조, 자원 관리 두 소제목과 역할 요약 소제목, 모듈 예시 불렛, 같은 열을 사용한 마지막 표; 세부 취향은 사용자 검토 전 |
| 원고 · 2 | 앞 절에서 들어와 다음 평가 절로 이어 읽을 수 있다. | 해당 연결 충족 | 원고 첫 문단과 §9 도입. 보고서 전체를 새로 작성·검증한 것으로 확대하지 않음 |
| 그림 조건 | 생성 없이 핵심 설명·빈 자리·캡션·주·스케치 구성을 준비했다. | 충족 | P4, E-F1 자리와 텍스트, §4의 피규어 검토 메모 |
| 자료 정합성 · 전 단계 | 설계 의도·코드 구현·측정 결과를 섞지 않는다. | 충족 | §1의 자료 대조; 시간·메모리 절감값이나 성능 수치를 새로 추가하지 않음 |

사용자 검토 상태: 원고가 원하는 의도로 나왔다는 평가와 플랜의 읽기 어려움에 대한 피드백을 받았다. 해설 후 사용자는 이해가 잘 되었고 U·M·P 같은 참조 표기를 유지해도 좋다고 밝혔다. 이 동의를 플랜 전체나 스킬 전체의 최종 승인으로 확대하지 않는다. 상세 내용은 §6에 기록한다.

## 5. 지침 후보와 보조 사례 검토

### 5.1 첫 사례에서 적용한 지침 후보

아래는 첫 예시 작성에서 적용한 후보이며, 사용자 피드백과 보조 사례 검토에 따라 정제한다.

| 후보 | 연결 그룹·단계 | 다른 글에도 적용할 판단 |
|---|---|---|
| 중심 기여를 먼저 말하고 하위 구현을 배치한다. | 2·4 / 스펙·플랜·원고 | 도입부가 배경·작업 고민을 길게 따라가느라 핵심을 늦추지 않는가. |
| 스펙의 설명 목표를 플랜에서 실제 동작·이유·조건으로 확장한다. | 5 / 플랜 | ‘무엇을 쓸 것인가’만 반복하지 않고, 독자에게 전달할 설명이 생겼는가. |
| 설명을 줄여도 작동 순서와 적용 범위를 유지한다. | 5·6 / 플랜·원고 | 정확성을 만드는 조건과 단순한 부연을 구별했는가. |
| 하위 소제목은 소속 핵심을 이해할 수 있도록 묶는다. | 3·7 / 플랜·원고 | 표시 구획 때문에 별도 핵심·승인 단위를 불필요하게 늘리지 않았는가. |
| 표는 항목마다 같은 비교 질문에 답하게 한다. | 5·7 / 플랜·원고 | 열의 의미가 각 행에서 같고, 본문에 필요한 설명을 표만으로 대체하지 않았는가. |

‘LM과 ITM을 예시로 든다’, ‘메모리·계산 재사용 소제목을 둔다’, ‘이 절의 표를 마지막에 둔다’는 이번 자료와 사용자 지시에 따른 선택이다. 모든 보고서에 고정 적용하는 규칙으로 만들지 않는다.

### 5.2 보조 사례의 범위와 진행 상태

기준 스펙의 구 §6에 있던 예시 보완 제안과 검토 범위를 옮겼다. 통합 증류기 한 사례는 기본적인 단계 연결을 확인하는 첫 사례다. 이 사례만으로 실패·개선 과정의 선별, 문서 전체의 흐름, 논문형 표현까지 충분히 검증했다고 보지 않는다. 사례 수 자체를 통과 기준으로 삼지 않는다.

| 사례 | 확인할 판단 | 2026-09-10 이관 당시 상태 |
|---|---|---|
| 통합 증류기 | 자료 풀 → 스펙 → 실제 설명을 담은 플랜 → 결과보고서형 원고의 연결 | 첫 예시 작성과 사용자 피드백 반영. 상세 이력은 §6에 기록 |
| ITC의 짧은 보조 사례 | 여러 실험과 실패·개선 기록에서 핵심을 선택하고, 필수 설명과 부록으로 옮길 내용을 구분 | 미실행 제안. 이번 이관에서 새 사례를 작성하지 않음 |
| 같은 내용의 결과보고서형·논문형 비교 | 목표·사실·필수 설명을 유지하면서 문단·소제목·연결 방식을 바꾸는 판단 | 기존 비교 초안을 [연결 예시 §4 끝](2026-09-09-integrated-distiller-writing-example.md#format-comparison)으로 이관. 검토안이며 두 형식을 항상 함께 출력하는 규칙은 아님 |

섹션 사례에는 앞뒤 연결을 포함하고, 전체 흐름 판단에는 문서의 목차와 섹션별 핵심 배열도 함께 참고한다. 사례 검토 후에도 중요한 판단이 모호하면 그 판단만 확인하는 짧은 추가 예시를 검토한다. 첫 사례의 특정 내용이나 구성을 모든 보고서의 필수 형식으로 일반화하지 않는다. 공통 지침으로 정제할 때에는 다른 주제의 짧은 자료에서도 적용 가능한지 확인하며, 필요하면 비교 결과와 해석 조건을 포함한 보조 예시를 사용한다. 이 추가 검토는 후보이며, 이번 이관에서 수행한 검증으로 기록하지 않는다.

### 5.3 사용자 피드백 반영과 공통 지침으로의 정제

사용자는 예시를 작성한 뒤 직접 피드백과 코멘트를 남기고, 이를 반영하여 사례와 지침을 수정하는 과정을 요청했다. 예시 검토는 초안 작성 → 사용자 코멘트 → 사례 수정과 지침 후보 갱신 → 수정본 검토 순서로 진행한다. 첫 사례의 피드백으로 기준을 다듬은 뒤 그 기준을 보조 사례에 적용한다.

코멘트별로 관련 위치 → 사용자 의도 → 예시에 반영한 수정 → 다른 글에도 적용할 지침 후보를 연결한다. 특정 실험의 사실 정정이나 해당 문서만의 강조점은 해당 사례·작성 조건에 반영하며, 공통 지침으로 확장할 때는 다른 사례에서도 타당한지 확인한다. 해석이 모호한 코멘트만 사용자에게 확인한다.

수정본에는 주요 변경 전후와 지침에 반영한 내용을 묶어 제시한다. 코멘트마다 별도 승인을 요구하지 않는다. 예시와 지침을 검토하는 현재 설계 과정은 실제 스킬 실행 시 새로운 승인 단계를 추가하는 규칙이 아니다. 첫 피드백과 해설 이후의 의견, 승인 범위는 §6에 기록한다.

## 6. 첫 예시의 진행 이력과 사용자 피드백

### 6.1 첫 연결 예시를 만든 배경과 범위

기준 스펙의 구 §6에 기록된 진행 이력이다. 처음에는 한 문장의 스펙 → 플랜 확장, 섹션·소제목 구분, 세 수준의 변경 판정 예시만 있었다. 같은 글감이 실제 설명과 완성 원고로 이어지는 예시가 없어, 자료 선택·포인터 사용·플랜의 상세도·원고 표현의 연결을 확인하기 어려웠다.

사용자가 첫 예시 작성을 승인하여 [검토용 예시 v0.1](2026-09-09-integrated-distiller-writing-example.md)과 이 자료 대조·자체 점검 메모를 작성했다. 첫 예시는 실제 보고서의 ‘통합 증류기’ 한 섹션으로, 사용자 피드백에 따라 경로 선택 기능을 중심에 두고 메모리·계산 관리를 하위 설명으로 배치했다. 실제 보고서 원고를 수정하거나 그림을 생성하는 작업과는 구분했다.

| 예시 구성 | 보여주려던 내용 |
|---|---|
| 작은 자료 풀 | 실제 자료 발췌와 위치, 사용자 강조점, 해당 섹션에 사용할 내용과 다른 곳에 둘 내용. 요약만 주지 않고 참조할 원자료를 연결한다. |
| 스펙 | 제목·하나의 설명 목표·우선 참조. 상세 구현 설명은 아직 펼치지 않는다. |
| 라이팅 플랜 | 같은 목표 아래 실제 설명 문장을 순서대로 배치한다. 각 설명에 사용한 자료가 어디인지 확인할 수 있게 하고, 피규어는 중심 메시지만 적는다. |
| 원고 | 같은 플랜을 연결된 문장과 적절한 구획으로 작성한다. 인접 섹션에서 들어오고 다음 섹션으로 이어지는 짧은 부분도 보여준다. 그림은 생성하지 않고 설명·캡션·각주만 작성한다. |
| 짧은 점검·수정 사례 | 목표 문장만 반복한 미충족 플랜 한 항목을 실제 설명으로 고친 뒤, 어떤 기준이 충족되었는지 위치와 함께 보여준다. |

결과보고서형 원고를 먼저 검토하고, 동일한 내용 일부를 논문형으로 표현한 짧은 비교를 그룹 6·7의 구체화에 활용하는 순서였다. 표현 방식이 달라져도 목표·사실·필수 설명은 유지하며, 실제 섹션 하나만으로 문서 전체의 구성 품질을 검증했다고 주장하지 않는다. 후속 보완 범위와 진행 상태는 §5.2에 구분했다.

### 6.2 첫 사용자 피드백 · 플랜의 읽기 어려움

**사용자가 확인한 내용:** 원고 결과물은 원하는 의도로 나왔다. 라이팅 플랜은 사람이 읽기 어려웠고, 어떻게 읽는지 설명을 요청했다.

**후속 사용자 의견:** 해설 후 이해가 잘 되었고 U·M은 그대로 두어도 되며, 항목들을 이런 표기로 부르는 방식이 괜찮다고 밝혔다. P와 M의 약자 뜻을 질문했다. 이에 P는 Plan, M은 Material, U는 User, S는 Section으로 안내했다.

**현재 대응:** U·M·P·S의 표기는 유지하고 예시 첫머리에 뜻과 사용 예를 추가했다. 플랜 전체의 재서식이나 보조 사례 작성은 아직 진행하지 않았다. 원고의 중심과 내용은 이번 변경 대상이 아니다.

**에이전트가 판단한 원인 후보:** P 번호가 설명 묶음·그림·표·다음 절 도입을 같은 깊이로 나열한다. 특히 P4는 P3을 보조하고 P6는 다음 절에 속하지만 그 관계가 목록 모양에서는 드러나지 않는다. 원고에 넣을 실제 설명과 배치 지시도 같은 문단에 섞였다. U·M의 식별자는 원자료 연결에 필요하지만 사람이 읽을 때는 이름을 다시 찾아야 한다. 이는 사용자에게 원인까지 확인받은 결론은 아니다.

**현재 표기의 의미:** S8은 스펙의 의미상 섹션, P1~P6은 이번 예시의 플랜 항목, U는 사용자 의도 기록, M은 원고·구현 자료다. P 하나가 반드시 원고 한 문단이나 독립 섹션이라는 뜻은 아니다. 독자는 P1의 중심 기능 → P2·P3의 실제 구현 → P5의 역할 요약 → P6의 다음 절 연결을 읽고, P4는 P3의 그림 후보로 확인한다.

**후속 의견을 반영한 지침 후보:** 참조 ID를 사용할 수 있으며, 뜻과 연결 방법을 처음에 한 번 안내한다. 이번 예시의 U·M·P·S는 유지한다. 처음 읽기 어렵다는 이유만으로 사용자에게 수용된 표기를 없애거나 모든 참조를 긴 이름으로 바꾸지 않는다. 실제 설명 내용과 원자료 연결은 유지하고, 설명·그림·표·다음 절 연결의 관계를 파악할 수 있게 한다. 플랜의 실제 설명을 ‘무엇을 설명하라’는 지시문으로 되돌리지 않는다.

**추가 점검 후보:** 표기 안내를 읽은 사용자가 플랜에서 ‘무엇을 말하는가 / 어떤 순서와 위계인가 / 어떤 설명을 보완해야 하는가’를 판단할 수 있는가. 첫 검토에서는 읽기 어려웠으나 해설 후 사용자는 이해했다고 밝혔다. 따라서 참조 ID 자체를 계속 미충족 문제로 남기지 않는다. 표기 유지에 대한 동의와 플랜 전체의 최종 검토는 구별한다.

### 6.3 그룹 6·7 구체화와 검토 상태

사용자는 그룹 6·7의 요약한 방향을 긍정적으로 평가하고 구체화를 요청했다. 기준 커밋 시점에는 기준 스펙 구 §4.1~§4.5의 8개 항목을 작성 행동·통과 조건으로 다듬고, 형식별 적용·수정 사례·자체 점검 순서를 연결했다. 구체화안은 한 묶음으로 검토하며, 항목별 추가 승인을 요구하지 않는 방향이었다.

형식 비교와 판정용 수정 사례는 이번 이관으로 각각 연결 예시와 이 메모 §3.4에서 관리한다. 사례의 원고 방향과 참조 표기에 대한 긍정적 평가를 전체 스킬 스펙이나 구현의 승인으로 확대하지 않는다. 현재 규칙과 미결정사항의 기준은 [스킬 설계 문서](2026-09-09-report-writing-skill-design.md)다.

### 7.2 판단 결과의 보존 검토

기준 스펙과 정리본을 읽어 아래 상황의 처리 결과를 대조했다. 스킬 실행 테스트가 아닌 문서의 의미·인계 조건 검토이며, 실제 SKILL.md는 아직 구현하지 않았다.

| 상황 | 정리 전후 동일하게 유지되는 판단 | 새 스펙 위치 |
|---|---|---|
| 작성 방향이 확인된 기존 초안에서 시작 | 조건·스펙·플랜 후보를 묶어 준비하고 각 단계 점검·승인 후 집필. 신규 집필에는 일반 단계 순서 적용 | §2 입력·§3.1·§3.6 |
| 조건·핵심은 승인되고 플랜 순서만 수정 요청 | 기존 승인은 보존하고 플랜과 영향 범위만 재검토. 미승인 묶음을 전체 승인으로 확대하지 않음 | §3.2·§3.6 |
| 최초 플랜에서 포인터 밖 자료가 필요 | 실제 자료를 읽고 승인 목표 안에서 확장. 자료 추가만으로 재승인하지 않으며 미채택 자료도 보존 | §2.2·단계 3 |
| 소제목을 추가하거나 기존 핵심을 분리 | 같은 설명을 묶으면 표현 보완, 필수 설명 변화는 플랜 변경, 독립 목표·범위 변화는 스펙 변경 | §2.1·§3.4~§3.5 |
| 필수 설명을 짧게 다시 작성 | 의미·조건·근거·해석 범위가 같으면 표현 보완. 정보 자체가 없어지거나 의미가 바뀌면 변경 규칙 적용 | §3.5·§4.2 |
| 체크 중 결함이나 근거 부족을 발견 | 기록만으로 통과시키지 않고 수정·재점검. 의존 범위의 확정은 보류하며 독립 작업은 계속 | §3.3·§3.5 |
| 논문형으로 쓰다가 가독성 개선 요청 | 기존 양식 안에서 표현을 개선. 핵심·근거·조건은 동일하게 보존 | §4.3~§4.4 |
| 검토안을 정리된 본문으로 이동 | 그룹 6·7·인계 경계·기타 재개 및 완료 기준은 검토 상태 유지. 리팩터링을 정책 승인으로 확대하지 않음 | 각 절 상태·§6 |

독립 검토에서도 기준 커밋의 32개 검토 묶음을 대조했으며, 검토 범위에서 중대한 누락·강도 변화·검토안의 확정 승격을 찾지 못했다. 이 과정에서 단계 4의 기존 원고를 선택 입력으로 명시하고, 단계 2 입력에도 기존 초안 후보 준비 예외를 연결했다.

### 7.3 내용·링크·수정 범위 확인

- 기준 스펙: 465줄 → 273줄. 줄바꿈 정규화·끝 공백 제거 기준 28,802자 → 16,478자.
- G6·G7의 지침·통과 조건 8개 행과 세 수준 변경 표 3개 행은 기준 커밋과 문자열 일치.
- 원래 연결 예시 본문·참조 표기·출처는 동일하며, 형식 비교와 이관 안내만 추가.
- 이동한 형식 비교 본문, 섹션 경계 사례 3개 행, 그룹 6·7 수정 사례 3개 행의 원문 보존 확인.
- README와 네 설계 문서의 로컬 링크 69개·앵커 참조 8개가 유효하며 앵커 중복 없음.
- 변경 파일은 기준 스펙·연결 예시·이 작업 메모·README 네 개. 과거 비판적 검토와 외부 보고서·실험 자료는 수정 대상에서 제외.
- Git 공백 검사 통과. 실제 스킬의 실행 품질은 후속 구현·검증에서 확인한다.

## 8. 2026-09-10 설계 검토 상태 정정

사용자는 “세부안 검토끝난거아님?”이라고 이미 진행한 검토의 완료 상태를 확인했다. 에이전트가 기존 ‘검토안’ 표기를 계속 유지하며 다시 검토해야 하는 것처럼 안내한 상태 기록을 정정했다.

그룹 6·7의 지침·통과 조건·형식별 적용·자체 점검과 단계별 완료·인계·진입·재개 세부 기준은 설계 검토 완료로 정리한다. 이 기준을 다시 승인받는 단계를 추가하지 않는다. 실제 미정 사항은 호출 이름과 실행 산출물·자료 풀·작업 기록의 파일 이름·저장 구성이며, 보조 사례는 구현·검증에서 활용할 후보로 둔다.

앞 절의 예시 제작·리팩터링 기록은 당시 기록으로 보존한다. 현재 결정 상태는 기준 스펙 §6을 따른다. 스킬 실행 중 개별 문서의 후보·내용·구조·진행 승인을 구별하는 규칙은 그대로 적용된다.

## 9. 2026-09-10 호출 이름과 HTML 산출물 지정

사용자는 호출 이름을 `report_writing:brainstorm / spec / writing plan / develop`처럼 구성하고 산출물은 HTML 보고서로 지정했다. 호출용 공백은 하이픈으로 정리하여 `report_writing:writing-plan`으로 표기한다. 하나의 작성 흐름을 네 단계의 진입점으로 제공하고, 각 단계에서 같은 자료·승인·진행 기록을 이어받는다. 피드백 스킬은 별도 후속 범위다.

최종 HTML과 중간 Markdown 자료를 구별하며, 경로 미지정 시 `reports/<report-id>/report.html` 및 `work/`를 운영 기본값으로 둔다. 사용자 지정 경로와 재개 시 기존 경로를 우선한다. §8에서 남겨 두었던 호출·출력 관련 사항은 이 후속 지시로 반영했으며, 현재 기준은 스펙 §1·§6이다.
