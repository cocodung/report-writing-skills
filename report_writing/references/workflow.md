# 공통 진행 계약

<a id="entry"></a>
## 진입

사용자가 명시적으로 호출한 단계에서 시작한다. 호출 이름만으로 선행 산출물의 내용·구조 승인이나 단계 전환 승인을 추정하지 않는다. 먼저 현재 요청, 제공 자료·초안, 기존 work 파일, 확인된 사용자 발언을 대조하여 다음을 판정한다.

| 입력 상태 | 진입과 준비 |
|---|---|
| 원자료만 있음 | 목적·독자·형식·강조점·범위를 확인하고 방향을 좌우하는 누락만 질문한다. brainstorm의 작성 조건과 큰 흐름부터 검토받는다. |
| 기존 초안만 있고 승인된 spec·writing-plan이 없음 | 조건·핵심·필수 설명·순서 후보를 추출하고 확인된 의도와 추정을 구별한다. [재개](#resuming)의 첫 묶음 검토 조건을 적용한다. |
| 승인된 spec이 있음 | 버전·승인 범위·작성 조건·자료 포인터와 writing-plan 진행 승인을 확인한다. 진행 승인만 빠졌다면 그것만 확인한다. |
| 승인된 writing-plan과 부분 원고가 있음 | 버전·승인 범위·집필 진행 승인, 기존 문단의 플랜 대응과 작성·점검 상태를 확인하고 develop을 재개한다. |

사용자가 지정한 경로를 우선하고, 재개 중인 기존 문서 루트가 확인되면 유지한다. 그 밖에는 [identity 계약](artifacts.md#identity)에 따라 기본 루트를 정한다. 이미 확정된 조건과 승인된 미변경 범위는 다시 묻지 않는다. 파일 존재나 근거 없는 승인 메모만으로 승인 사실을 추정하지 않는다. 입력이 부족한 직접 호출은 필요한 선행 준비를 하되 내부 후보를 승인 결과로 확정하지 않는다.

매 진입에는 이 절과 [승인](#gates), [자체 점검](#checks)을 적용한다. 변경이 생기면 [변경](#changes), 기존 초안이나 재개이면 [재개](#resuming)도 적용한다.

<a id="gates"></a>
## 승인과 단계 전환

단일 에이전트가 해당 단계의 모든 범위와 전체 산출물을 먼저 점검·수정하고, 정리된 단계 전체를 사용자에게 제시한다. 사용자가 분할 검토를 요청한 경우에만 지정 범위로 나눈다. 섹션별·문단별 승인이나 별도의 표현 승인 단계를 추가하지 않는다.

다음 네 조건이 모두 충족될 때만 다음 단계로 넘어간다.

1. 적용되는 자체 체크가 충족되었다.
2. 제시한 현재 버전·범위의 내용이 승인되었다.
3. 같은 버전·범위의 구조가 승인되었다.
4. 다음 단계 진행이 승인되었다. develop에서는 원고 완료 승인을 기록한다.

사용자 한 답변이 내용·구조·진행을 명시적으로 함께 승인하면 같은 발언을 세 항목의 근거로 연결한다. 사용자의 구체적 지시는 그 지시가 정한 범위에서 승인 근거로 인정한다. 기존 승인된 미변경 범위와 진행 승인은 유지한다. 부분 승인이나 특정 부분의 긍정적 의견을 전체 승인으로 넓히지 않는다.

자료 풀의 설명 후보·선택 이유·검토 중 순서는 내부 기록이다. 사용자에게 제시하지 않은 후보를 승인 결정으로 바꾸지 않는다. 변경 범위 승인은 수정안을 준비할 권한이며, 구체적으로 제시하지 않은 새 설명의 승인이 아니다. 미승인 범위는 수정하거나 필요한 질문을 해결하고, 승인 대기 중 준비한 제안은 승인된 원고로 확정하지 않는다.

<a id="checks"></a>
## 자체 점검

각 체크에는 단계, 적용 범위, 기준 ID, 확인 조건, 상태, 확인 위치와 짧은 근거, 필요한 수정을 남긴다. 상태는 `미확인 / 미충족 / 충족 / 해당 없음`이다. `해당 없음`은 그림처럼 실제 적용 조건이 없는 조건부 기준에만 쓰고 이유를 적는다.

- 통과는 검토 행동이 아니라 요구 상태가 충족되었다는 뜻이다. 발견한 결함을 기록만 하고 통과시키지 않는다.
- 필수 항목을 삭제하거나 해당 없음으로 처리하지 않는다.
- 근거가 부족하거나 확인하지 않은 항목은 충족으로 표시하지 않는다.
- 내용·구조가 바뀌면 영향을 받는 체크를 다시 확인한다. 옛 체크를 새 버전의 현재 충족으로 복사하지 않는다.
- spec은 모든 의미상 섹션과 하위 목표를 묶는 상위 섹션, writing-plan은 모든 S/P와 설명 문장, develop은 문단·문장과 섹션 사이 연결을 확인한다. 표시용 소제목은 소속 섹션 안에서 확인한다.
- 모든 단계의 마지막에는 ALL-G12로 작성 조건, 전체 누락·중복·순서·흐름을 확인한다.

점검과 승인 기록은 독자용 원고가 아닌 [state](artifacts.md#state)에 둔다.

<a id="changes"></a>
## 변경

변경 수준은 문장 수나 제목 추가 여부가 아니라 승인된 결정의 의미가 달라지는지로 판정한다.

| 수준 | 판단과 예 | 처리 |
|---|---|---|
| 표현 보완 | 핵심·범위, 필수 설명·근거의 의미, 논리적 의존관계를 유지한다. 문단 분리·병합, 같은 내용을 묶는 소제목, 의미를 보존한 제목 수정, 연결 문장·용어 풀이·출처 표기 보완이 해당한다. | 수정하고 관련 체크를 다시 확인한다. 별도 재승인 없이 현재 단계의 전체 검토에 포함한다. |
| writing-plan 변경 | 핵심은 유지하지만 필수 설명의 추가·삭제, 근거가 뒷받침하는 내용, 논리적 의존관계가 달라진다. | 해당 플랜과 의존 원고의 구체적 변경안을 한 묶음으로 승인받고 기존 spec 핵심의 보존을 확인한다. |
| spec 변경 | 핵심·설명 범위·역할이나 주요 논리 구성이 달라진다. | spec 수정안과 관련 플랜의 영향 범위를 함께 제시해 승인받은 뒤 갱신한다. 목적·독자·필수 형식도 바뀌면 brief 조건을 함께 변경 대상으로 제시한다. |

실질 변경은 기존 결정, 구체적 수정안, 이유, 표현/플랜/스펙 구분, 영향 위치를 한 묶음으로 만든다. 본문뿐 아니라 요약·결론·그림 설명·각주·상호 참조의 의존 범위를 확인한다. 승인된 미변경 범위는 다시 승인받지 않는다. 대기 중에는 영향받지 않는 작성·점검을 계속하고 의존 부분은 검토용으로 준비할 수 있으나 확정하거나 다음 단계로 넘기지 않는다.

승인 후 대응, 버전, 승인 범위를 갱신하고 영향받는 체크와 전체 흐름을 다시 확인한다. 한 변경 묶음의 승인을 다른 실질 변경의 포괄 승인으로 확대하지 않는다. 자료가 주장을 지지하지 않으면 근거에 맞는 수정안을 제시하고 의존 범위의 확정을 보류한다.

<a id="resuming"></a>
## 기존 초안과 재개

진입점은 가장 뒤 단계 파일의 존재가 아니라 확인된 작성 조건·승인 범위·남은 작업으로 정한다. 제공된 조건·자료와 좋은 문단을 재사용하고, 승인 뒤 바뀐 결정만 확인한다. 현재 사용자가 특정 파일을 승인된 플랜으로 지정해 계속 쓰라고 한 발언도 유효한 승인·진행 근거다.

기존 초안의 첫 진입에서 목적·독자·형식·강조점·범위·큰 흐름을 정리할 수 있고 핵심 선택을 바꿀 질문이 없으면 brainstorm·spec·writing-plan의 SKILL.md를 읽어 각 단계 후보를 만들고 자체 점검한다. 작성 조건 → 섹션별 핵심 → 실제 설명·순서의 대응과 유지·변경 대상을 한 묶음으로 제시한다. 후보를 준비하는 사이 단계별 중간 승인을 요청하지 않는다.

사용자가 묶음의 내용·구조와 집필 진행을 승인하고 각 단계 체크가 충족되면 develop에 진입한다. 일부만 승인되면 해당 버전·범위의 승인을 보존하고 미승인 부분과 의존 범위만 다시 검토한다. 핵심 불확실성이 남거나 사용자가 단계별 검토를 원하면 정상 순서로 검토한다. 이 예외는 기존 초안의 첫 묶음 검토에만 적용하며, 원자료만 있는 신규 문서의 단계를 줄이지 않는다.

재개에는 대상·수정 범위·작성 조건·최신 지시 위치, 산출물별 경로와 버전, 승인 범위와 근거, S/P별 작성·점검 상태, 남은 일, 미해결 질문·변경안·영향 범위, 승인 대기 중 가능한 독립 작업을 [state](artifacts.md#state)에 남긴다. 빠진 포인터나 기록은 필요한 범위만 복원한다.
