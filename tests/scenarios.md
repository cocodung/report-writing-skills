# 실행 시나리오

평가 대상 에이전트에는 해당 시나리오의 요청, 시작 상태, 지정 자료만 제공한다. 기준 실행에는 구현 계획·설계 스펙·루브릭·대상 스킬을 제공하지 않는다. 스킬 실행에는 대상 SKILL.md와 그 스킬이 가리키는 패키지 참조를 제공한다. 두 실행은 새 문맥과 같은 모델·추론 설정을 사용하고, 생성물은 `.work/validation/<case>/<run>/`에 둔다.

## B-1 · 원자료에서 글감과 짧은 작성안 만들기

- 시작 상태: 신규 문서. 승인된 작성 조건·brief·spec·writing-plan이 없다.
- 자료: `tests/fixtures/kiosk/materials.md`
- 최초 요청:

> 이 자료로 팀의 개발 결과보고서를 준비하자. 독자는 제품 책임자다. 가독성을 중시하고 피규어는 만들지 말자. 기능 변경과 성능 중 무엇을 중심에 둘지는 아직 고민 중이다. 우선 글감과 짧은 작성안을 잡아줘.

- 핵심 강조점을 묻는 경우의 후속 응답:

> 중심은 방과 시간을 함께 선택하도록 흐름을 바꾼 이유와 구현이야. 관측 결과는 그 뒤에 제한을 포함해 보여주고, 추가 평가는 계획으로 남겨.

- 원자료에 없는 통합 동기와 승인 범위를 확인하는 경우의 보완 응답:

> 원자료에 없는 동기를 추가할 필요는 없고, 확인된 화면 구성 변화와 최종 확인 유지 이유 중심으로 잡아줘. 지금은 작성안 검토만 하는 것이고 스펙 진행을 승인한 것은 아니야.

실제 B-1 비교 실행에서는 같은 의미를 다음과 같이 구체화해 양쪽에 동일하게 제공했다.

> 원자료에 없는 방·시간 통합 동기를 새로 넣을 필요는 없어. 확인된 화면 구성의 변화와 최종 확인을 유지한 이유를 중심으로 작성안을 확정해줘. 관측·제한·추가 평가의 구분은 유지하자. 이전 응답은 보존하고 이번 응답은 response-scope.md에 저장해줘. 스펙으로 진행하라는 승인은 아직 아니고, 지금은 전체 작성안을 검토할 수 있게 준비해줘.

- 허용 출력: 실행별 폴더 안의 응답 원문과 `brief.md`, `materials.md`, `state.md`.
- 관찰 초점: 의도·관측·계획의 구분, 전체 흐름, 최초 불확실성 확인, 자료 접근 보존, 승인되지 않은 다음 단계의 확정 방지.

질문 개수나 특정 문구는 통과 조건이 아니다. 최초 응답이 질문 없이 완성안을 제시하면 후속 응답을 전달해 반영 결과도 보존한다. 원자료에 없는 통합 동기를 묻는 것은 정당한 자료 확인이며, 위 보완 응답은 비교 실행 양쪽에 동일하게 제공한다.

## S-1 · 승인된 작성안에서 전체 스펙 만들기

- 시작 상태: B-1의 작성 조건과 큰 흐름이 승인되었고 spec 진행도 명시적으로 승인되었다. `brief.md`에는 제품 책임자용 개발 결과보고서, 결과보고서형 가독성, 피규어 미생성 조건과 `기능 변경의 선택 이유와 구현 → 관측 결과와 한계 → 후속 평가`의 순서가 있다.
- 자료: `tests/fixtures/kiosk/materials.md`
- 요청:

> 작성 조건과 큰 흐름은 승인한다. 기능 변경의 선택 이유와 구현 → 관측 결과와 한계 → 후속 평가의 순서로 스펙을 작성해줘. 스펙에는 제목별 핵심과 참조만 짧게 보고 싶다.

- 허용 출력: 실행별 폴더 안의 응답 원문과 `work/spec.md`, `work/materials.md`, `work/state.md`. 시작 brief는 입력으로 보존한다.
- 관찰 초점: 독립 목표 분리, 관측의 동일 참여자·고정 순서 조건, 실제 원문을 가리키는 위치와 참조 이유, 전체 스펙의 간결한 제시, S-G3~S-G5·ALL-G12 및 승인·진행 기록.

스펙은 사용자에게 제목별 핵심과 참조를 짧게 보여주되, 조건을 숨길 만큼 압축하지 않는다. 모든 S의 체크를 state에 기록한 뒤 다시 섹션별 승인을 요구하면 미충족이다. 상세 후보와 점검 기록은 사용자 검토용 스펙의 모든 행에 늘어놓지 않고 work에서 구별한다.

## P-1 · 승인된 스펙을 실제 설명의 라이팅 플랜으로 확장하기

- 시작 상태: 아래 `키오스크 스펙 v0.1`의 내용과 구조가 승인되었고 writing-plan 진행도 현재 요청으로 명시적으로 승인되었다. 작성 조건은 제품 책임자에게 구현의 선택 이유를 먼저 설명하는 결과보고서이며, 가독성을 중시하고 그림은 텍스트와 자리만 준비한다.
- 자료: `tests/fixtures/kiosk/materials.md`
- 고정 스펙:

> # 키오스크 스펙 v0.1
> 작성 조건: 제품 책임자에게 구현의 선택 이유를 먼저 설명하는 결과보고서.
> 표현 방식: 가독성 중시. 그림은 텍스트와 자리만.
> S1 · 선택과 확인을 나눈 예약 흐름
> 핵심: 방·시간 선택을 통합하되 최종 확인을 유지한 구현과 선택 이유를 설명한다.
> 우선 참조: M1 — 화면 구성과 확인 화면 유지 이유.
> S2 · 같은 참여자에게서 관측한 완료 시간과 성공
> 핵심: 같은 12명이 A 다음 B를 사용했을 때의 차이와 그 해석 한계를 설명한다.
> 우선 참조: M2 — 시간·성공 정의·고정 순서.
> S3 · 효과를 구분하기 위한 후속 평가
> 핵심: 고정 순서의 한계를 보완할 추가 평가 계획을 설명한다.
> 우선 참조: M3 — 아직 수행하지 않은 순서 균형 평가.

- 요청:

> 이 스펙의 내용과 구조를 승인하니 라이팅 플랜으로 확장해줘. 각 제목 밑에 실제 전달할 설명이 있어야 해. 그림이 필요하면 핵심만 적어줘.

- 허용 출력: 실행별 폴더 안의 응답 원문과 `work/writing-plan.md`, `work/materials.md`, `work/state.md`, 필요한 경우 `work/figures.md`. 시작 spec은 입력으로 보존한다.
- 관찰 초점: 실제 설명과 근거·조건·순서, 연결된 원문과 전체 자료 풀의 사용, S/P 및 표·그림·다음 절 연결의 소속, P-G3~P-G5·ALL-G12와 승인·진행 기록.

S1의 우선 참조는 M1뿐이지만 포인터는 자료 접근을 제한하지 않는다. S2·S3에 필요한 M2·M3을 연결하고 M4는 관련성이 확인되지 않으면 수록하지 않을 수 있다. 첫 확장에서 승인된 목표 안의 하위 설명과 포인터를 선택하는 일에 별도 변경 승인을 요구하지 않는다.

## D-1 · 승인된 플랜을 결과보고서형 HTML로 작성하기

- 시작 상태: P-1에서 검증을 통과한 writing-plan의 내용과 구조가 승인되었고 develop 진행도 현재 요청으로 명시적으로 승인되었다. 작성 조건은 제품 책임자용 개발 결과보고서, 가독성 중시, 그림은 생성하지 않고 빈자리와 설명만 준비하는 것이다.
- 자료: P-1 스킬 실행의 승인된 `work/writing-plan.md`, 연결된 `work/materials.md`와 원자료, `work/state.md`, 필요한 그림 핵심이 있는 `work/figures.md`.
- 요청:

> 이 플랜의 내용과 구조를 승인하니 HTML 보고서로 작성해줘. 결과보고서로 가독성을 높여줘. 그림은 빈자리와 설명만 준비해.

- 허용 출력: 실행별 폴더 안의 응답 원문, `reports/kiosk/report.html`, 갱신한 `work/state.md`, 필요한 경우 갱신한 `work/figures.md`.
- 관찰 초점: 승인된 실제 설명과 조건의 의미 보존, 결과보고서형 위계와 이어 읽는 흐름, 독자용 출처·각주 링크, 같은 그림 ID의 빈자리·캡션·각주·제작 메모 연결, D-G345·G6-1~G7-4·ALL-G12와 완료 승인 경계.

결과보고서형은 훑을 때 핵심과 하위 설명의 관계가 보이고 이어 읽을 때 이유·구현·관측·제한·후속 계획이 연결되어야 한다. 표나 불렛의 존재 자체를 통과로 판정하지 않는다.

## D-2 · 논문형 안에서 가독성 높은 HTML 작성하기

- 시작 상태와 자료: D-1과 같은 승인된 P-1 내용과 원자료를 독립된 새 실행에 제공한다. 필수 형식은 논문형이며 develop 진행이 승인되었다.
- 요청:

> 필수 형식은 논문형 문단 중심이야. 이 형식 안에서 가독성을 높여 HTML로 써줘.

- 허용 출력: D-1과 같다.
- 관찰 초점: D-1과 같은 필수 의미·근거·조건의 보존, 논문형 문단 중심 배치, 문단 요점과 문단 사이 논리 연결, 비교에 필요한 표·그림의 양식 내 사용, 독자용 출처와 durable state·figures 인계.

D-2는 가독성 요청을 이유로 결과보고서형 불렛 중심 구조로 바꾸지 않는다. D-1과 D-2의 설명량·정확성 기준은 같으며 런타임이 두 버전을 함께 만들 필요는 없다.
