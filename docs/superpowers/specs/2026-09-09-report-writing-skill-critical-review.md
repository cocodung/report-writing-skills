# 보고서 작성 스킬 설계 · 승인 전 비판적 검토

검토일: 2026-09-09

검토 대상: [report-writing-skill-design.md](2026-09-09-report-writing-skill-design.md)

대상 SHA256: `2060E7E5714D7FE5914A25F2D1EE63EB021F7EA7949D08E99BC6FD4A4DC4504F`

본문의 행 번호는 위 버전 기준이다. 설계 원문은 이번 검토에서 수정하지 않았다.

후속 논의에서 사용자는 R1의 설명 목표·실제 설명 구분, R2의 자료 인계 방식, R4의 섹션·표시용 소제목 경계, R5의 결과 기준 점검 등을 구체화했고 첫 실제 예시도 검토했다. 현재 요구사항과 결정 상태는 [최신 설계 문서](2026-09-09-report-writing-skill-design.md)를 기준으로 읽는다. 아래 검토 본문은 당시 버전의 문제와 제안을 보존한 기록이며, 현재 미해결 항목 목록이나 별도의 구현 스펙으로 사용하지 않는다.

## 판단

네 단계의 역할과 사람이 승인할 범위는 대체로 정리되어 있다. 다만 이 문서를 그대로 구현 계획으로 넘기면, 에이전트에 따라 플랜의 상세도, 다음 단계가 읽을 자료, 승인된 결정의 범위와 체크 통과 판정이 달라질 수 있다. 아래의 필수 보완을 반영한 뒤 스킬 구현용 스펙으로 승인하는 것을 권한다.

현재 요청은 스킬 설계를 구현 계획으로 옮길 때의 해석 가능성을 검토하는 것으로 보았다. 그 판단을 위해 설계 안의 보고서 스펙시트 → 라이팅 플랜 전환도 구체적인 사례로 검토했다. 단일 에이전트 집필 절차를 바꾸지 않고, 별도의 두 검토 에이전트 의견과 주 에이전트의 검토를 종합했다. 실제 스킬 실행이나 실험 사실 재검증은 수행하지 않았다.

우선순위의 의미:

- **P1:** 핵심 작업이나 단계 통과 여부가 달라지므로 구현 계획 작성 전에 보완할 사항.
- **P2:** 특정 상황에서 승인 횟수나 단계 대응이 달라지는 문구·경계 보완 사항.

## R1 · P1 · 플랜의 설명 문장이 실제 내용인지 집필 지시인지 구별되지 않음

**위치:** 53–57행, 65–67행.

‘짧은 문장이나 문장형 항목’에는 “메모리 최적화 방안을 설명한다”와 “활성화한 증류 경로에 필요한 티처 모듈만 GPU에 올린다”가 모두 들어갈 수 있다. 전자는 작성할 주제만 정하고, 후자는 실제 전달할 내용을 정한다.

첫 방식으로 플랜을 만들면 라이팅 단계에서 필수 설명과 근거를 처음 선택하게 된다. 그러면 승인된 플랜을 보존했는지, 플랜 변경이 발생했는지 판정할 수 없다. 사용자가 원한 ‘핵심 아래 설명의 뼈대를 세우고 검토한 뒤 쓰기’와 직접 연결되는 결함이다.

**제안 문구:**

> 라이팅 플랜의 설명 문장은 원고에 담을 실제 설명 내용을 포함한다. “방법을 설명한다”, “결과를 비교한다” 같은 집필 지시나 주제명만으로 대신하지 않는다. 근거를 사용하는 문장은 어떤 자료로 무엇을 어느 범위까지 설명하는지 알 수 있어야 한다. 최종 문구와 문단 경계는 라이팅 단계에서 다듬는다.

**경계 사례:**

- 부족: “증류 조합 선택을 설명한다. 메모리 최적화를 설명한다.”
- 충분한 뼈대: “설정에서 ITC·ITM·LM을 각각 켜고 끈다. 활성 경로에 필요한 티처 모듈만 GPU에 올린다.”

문장 수나 분량 제한을 추가하기보다, 읽었을 때 실제 설명 내용을 알 수 있는지를 판정하는 편이 적절하다.

## R2 · P1 · 스펙에서 플랜으로 넘기는 필수 입력이 정의되지 않음

**위치:** 20행, 45행, 53행, 103행, 143행, 221행.

45행은 필수 설명과 자료 위치를 작업 기록에 남긴다고 한다. 그러나 53행은 플랜 작성의 출발점으로 승인된 스펙시트만 명시한다. 다음 에이전트가 제목과 핵심만 읽고 설명을 새로 선택해도 명확한 위반으로 보기 어렵다.

파일 이름과 폴더는 구현 과정에서 정할 수 있지만, 어떤 정보를 반드시 넘기고 읽어야 하는지는 지금 결정해야 한다. 짧은 스펙을 유지하려면 별도 작업 기록의 전달이 특히 중요하다.

**제안 문구:**

> 라이팅 플랜은 승인된 스펙시트, 작성 조건, 해당 스펙 버전에 연결된 자료·필수 설명 기록을 함께 읽고 시작한다. 작업 기록에는 대응 섹션, 관련 원자료의 위치, 설명 후보와 필요한 해석 조건을 남긴다. 기록이 누락되면 원자료에서 복원하거나 필요한 정보를 확인하며, 핵심만 보고 필수 내용을 추측하지 않는다.

**최소 인계 내용 제안:**

| 내용 | 목적 |
|---|---|
| 작성 조건과 사용자 강조점 | 독자·형식·중요한 전달 의도를 유지 |
| 승인된 스펙의 버전과 섹션 대응 | 어느 제목·핵심을 확장하는지 확인 |
| 설명 후보·자료 위치·해석 조건 | 핵심을 뒷받침하는 내용을 이어받음 |
| 현재 단계·승인 범위·미해결 사항 | 파일 존재를 승인으로 오인하거나 기존 승인을 반복하지 않음 |

재개할 때도 대화와 이 기록으로 확인되는 승인은 유지한다. 파일이 있다는 이유만으로 승인되었다고 간주하지 않고, 확인되지 않는 상태만 사용자에게 확인한다.

## R3 · P2 · 내부 작업 기록과 승인된 결정의 경계가 없음

**위치:** 41–49행, 103행, 133행, 158–166행.

사용자는 제목과 핵심을 검토하지만, 에이전트는 별도 기록에 필수 설명과 조건을 남긴다. 이 기록까지 승인된 결정으로 취급하면 최초 플랜을 만드는 정상적인 설명 선택에도 변경 승인을 요청할 수 있다. 반대로 작업 기록을 전혀 제약 없는 메모로 취급하면 핵심의 성립 조건을 버릴 수 있다.

3.5절의 제목이 ‘라이팅 중’이므로 단계 4에 적용된다고 읽는 것이 자연스럽다. 따라서 최초 플랜 작성이 항상 변경 승인 대상이라는 직접적인 모순은 아니다. 다만 내부 기록의 지위와 비교할 승인 기준선이 없어서 다른 구현이 가능하다.

**제안 문구:**

> 핵심의 의미나 성립 범위를 바꾸는 조건은 사용자 검토용 핵심 문장에 포함하거나 그 문장에 짧게 연결해 표시한다. 내부 기록의 설명 후보와 순서는 아직 승인된 결정이 아니다. 최초 라이팅 플랜은 승인된 핵심·범위 안에서 설명을 구체화하는 정상 작업이며 전체 플랜으로 검토받는다. 변경 분류는 이미 승인된 결정과 비교해 적용한다.

이렇게 하면 스펙을 짧게 유지하면서도, 사용자에게 보여주지 않은 결정에 승인 효력을 부여하지 않는다.

## R4 · P2 · 의미상 섹션과 표시용 소제목이 충돌함

**위치:** 91행, 153행, 164행, 172행.

91행은 하위 제목을 각각 별도 섹션으로 점검하도록 한다. 반면 164·172행은 기존 내용을 묶는 소제목을 표현 보완으로 추가할 수 있게 한다.

예를 들어 승인된 ‘통합 증류기’ 섹션 안에 ‘메모리 관리’라는 소제목을 추가하면, 한 구현은 새 섹션·핵심·스펙 대응을 요구하고 다른 구현은 기존 섹션 내부의 표시로 처리한다. 문서가 의도한 자율 편집 범위에 실제로 영향을 준다.

**제안 문구:**

> 섹션은 스펙에서 제목·범위·핵심을 배정한 내용 단위다. 원고에서 가독성을 위해 추가한 소제목은 해당 섹션 안의 표현 구획으로 두며, 독립된 핵심이나 범위를 만들 때에만 새로운 스펙 섹션으로 본다. 하위 제목을 별도 섹션으로 점검한다는 규칙은 스펙에 정의된 하위 섹션에 적용한다.

## R5 · P1 · 체크리스트가 결함 해소보다 점검 수행을 묻는 경우가 있음

**위치:** 115행, 137–141행, 147행, 152–153행.

“빠진 필수 설명과 중복을 점검했는가”는 누락을 발견하고 그대로 기록한 경우에도 ‘예’가 될 수 있다. “전체 흐름의 누락·중복·순서를 확인했는가”도 확인 결과가 적합한지를 요구하지 않는다. 일반 규칙의 ‘미충족이면 수정’만으로는 무엇을 미충족으로 판정할지 정해지지 않는다.

**제안 문구:**

> 체크리스트 통과는 점검 수행이 아니라 요구한 상태의 충족을 뜻한다. 발견한 미해결 결함이 있으면 해당 항목은 미충족이다. 각 항목은 적용 범위·통과 조건·확인 근거를 가지며, 단순히 “검토했는가”라는 수행 여부만으로 작성하지 않는다.

**변경 예:**

- 기존: “빠진 필수 설명과 중복을 점검했는가.”
- 수정: “이 섹션에서 필요하다고 선정한 설명이 플랜에 모두 대응하고, 역할 없이 반복되는 설명이 남아 있지 않은가.”
- 기록: 어느 설명 문장이 어떤 필수 설명을 담당하는지, 미충족이면 무엇이 빠졌는지 남긴다.

또한 147행은 세부 항목을 여전히 후보로 둔다. 필수 항목과 조건부 항목을 구현자가 임의로 정하지 않도록, 최소 체크리스트는 설계 승인 전에 확정할 필요가 있다.

## R6 · P2 · 변경 범위 승인이 미작성 산출물 승인으로 확대될 수 있음

**위치:** 166행, 182–184행.

스펙 수정안과 ‘관련 플랜의 변경 범위’를 승인받은 뒤 실제 플랜과 원고를 새로 작성하는 상황이 가능하다. 이때 변경 묶음의 진행 승인을 아직 제시하지 않은 설명 선택의 내용·구조 승인으로까지 기록할 여지가 있다.

부분 승인을 전체 승인으로 확대하지 말라는 기존 규칙은 좋다. 여기에 ‘검토한 실제 내용’과 ‘작성해도 되는 변경 범위’를 구분하는 한 문장이 필요하다.

**제안 문구:**

> 변경 범위의 승인은 그 범위 안에서 수정안을 작성할 수 있다는 뜻이며, 아직 제시하지 않은 새로운 설명 결정의 내용·구조 승인까지 포함하지 않는다. 이미 제시한 구체적인 수정 내용이나 사용자가 직접 지시한 결정은 기존 승인으로 인정한다. 그 밖의 새 결정만 다음 산출물 검토에 묶어 제시한다.

이 원칙을 적용하더라도 섹션별 사람 승인을 추가할 필요는 없다.

## 이미 명시되어 있지만 승인 전에 정할 사항

다음은 숨은 결함으로 세지 않았다. 6절에서 미확정으로 밝혀 두었으나, 그대로 두면 구현 계획 작성자가 사용자의 집필 선호를 대신 결정하게 된다.

1. **그룹 6·7의 실제 판정 기준.** 196행의 결과보고서형 지침은 제목·불렛·여백·표 사용과 재배치까지만 정한다. 사용자 피드백의 정확한 기술 용어 사용, 불필요한 도입 제거, 해결 방향 선제시, 필요한 줄글 보존 등이 실제 작성 규칙으로 충분히 정의되지 않았다. 모든 문단을 불렛으로 바꾸거나 기술 용어를 추상어로 바꾸는 결과도 막아야 한다. 논문형 역시 문단 첫 문장에 핵심을 두는 것과 문장 간 설명 관계를 함께 판정해야 한다.
2. **브레인스토밍의 산출물과 종료 조건.** 목적·독자·형식·강조점이 정리되고 스펙 선택을 좌우하는 질문이 해소되면 작성 조건과 글감 범위를 제시해 승인받는 등, 단계 1을 완료할 수 있는 관찰 가능한 기준이 필요하다.
3. **기존 초안으로 시작할 때의 진입 방식.** 기본적으로 네 단계를 거치되 이미 확인된 자료·의도는 재사용할지, 승인된 스펙·플랜이 있는 경우에는 어느 단계에서 재개할지 정해야 한다. 파일명과 스킬 이름 자체는 구현상의 선택으로 남겨도 된다.

명칭도 한 문장으로 구분해 두는 편이 좋다. 현재 문서는 스킬의 구현 설계이며, 그 안의 스펙시트·라이팅 플랜은 보고서 집필 산출물이다. Superpowers의 소프트웨어 구현 계획을 보고서의 라이팅 플랜 대신 자동 호출한다는 의미로 읽히지 않게 한다.

## 수정 후 확인할 사례

이 표는 실제 실행 시험 결과가 아니라, 수정 스펙을 다시 읽을 때 동일한 판단이 나오는지 확인할 사례다.

| 상황 | 기대하는 판단 |
|---|---|
| 플랜에 “실험 결과를 설명한다”만 있음 | 실제 설명 내용이 없으므로 미충족 |
| 같은 핵심 아래 기존 내용을 묶는 소제목을 추가 | 표현 보완, 새 스펙 섹션이나 재승인 요구 없음 |
| 스펙에서 플랜으로 넘어가며 원자료와 작업 기록이 빠짐 | 기록 복원·확인 후 진행, 핵심만 보고 설명을 추측하지 않음 |
| 최초 플랜에서 승인된 핵심을 설명하는 내용을 구체화 | 정상적인 단계 3 작성, 완성된 전체 플랜으로 검토 |
| 필수 설명 누락을 발견했지만 기록만 남김 | 해당 체크 항목 미충족, 단계 전환 불가 |
| 스펙 변경 방향만 승인받고 새 설명을 작성 | 새 설명 결정은 전체 산출물 검토에 포함, 미리 승인된 것으로 간주하지 않음 |

## 제안하는 다음 작업

R1·R2·R5를 먼저 명문화하고 R3·R4·R6의 경계 문구를 추가한다. 이어 미확정인 최소 작성·점검 기준을 채운 다음, 한 개의 실제 보고서 섹션으로 스펙 → 플랜 → 원고 예시를 나란히 만들어 검토한다. 이렇게 하면 사용자가 승인할 때 구현자의 재해석에 맡겨진 부분을 확인할 수 있다.

검토 결과와 수정 문구는 이 문서에 제안으로 남겼다. 기존에 승인된 네 단계, 단일 에이전트의 전체 섹션 점검, 단계 전체 산출물 승인, 그림 생성 금지, 세 수준의 변경 분류는 유지하는 방향이다.
